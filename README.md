# 论文助手 · 四合一站点

把四个论文助手整合成一个公网可访问的网站：**题目生成 → 资料获取 → 写作 → 评估**。

> **想看"有哪些智能体"？** → [agents/](agents/README.md)
> 本机 **19 个写作智能体**的完整索引（13 个能力层 + 6 个板块层）、
> 六板块流水线为什么这么排、以及本机其它 7 个写作项目的说明文档。
> 那份索引还标注了**版本谱系**——本仓库是 Python 六板块版，更新一代的
> "研序"七阶段版在 `codex/writing-workspace`，不在本仓库内。

访客**自带 API Key**（下称 BYOK，Bring Your Own Key）：密钥只存在访客浏览器里，
随每次请求经请求头转发给模型服务商。服务器不保存、不缓存、不回退使用站主的密钥，
也不把它写进日志。站点也可以改为"本站出 Key"形态（见第三节）。

## 一、四个助手分别来自哪里

| # | 助手 | 实现来源 | 是否需要 Key |
|---|---|---|---|
| ① | 题目生成 | `thesis-topic-helper` 的 `core/` 整包 | 否（可离线） |
| ② | 资料获取 | `thesis-agents` 的文档解析 + 外部核验 | 抽取需要；核验不需要 |
| ③ | 写作 | 新增的「只依据证据」写作链路 | 是 |
| ④ | 评估 | `thesis-agents` 的 53 个检查器 + 审稿意见书 | 检查不需要；意见书需要 |

上游两套代码**一行都没有改**，以原样隔离在 `vendor/` 下（见第二节）。
本站自己的代码只有 `suite/` 目录，约 2000 行。

## 二、关键设计：为什么上游代码能原样复用

两套上游项目各自通过**相对项目根的目录深度**推导数据目录、`.env`、导出目录
（例如 `PROJECT_ROOT = Path(__file__).resolve().parent.parent`），并且包名撞车：

| 上游项目 | 包名 | 与另一套的冲突 |
|---|---|---|
| `thesis-agents` | `app` | `config` / `llm` / `server` 三个模块同名 |
| `thesis-topic-helper` | `core` | 同上 |

直接平铺会同时踩两个坑：算错根目录（把文件写进代码目录）、同名模块互相覆盖。

**解法是给每套代码一个"隔离层"**，让它自己算出的根目录正好落在自己的层里：

```
vendor/
  thesisapp_stage/          <- thesis-agents 的隔离层
    app/                    <- 原样搬运，256 处相对导入一个字没改
  topichelper_stage/        <- thesis-topic-helper 的隔离层
    core/                   <- 原样搬运
```

两个导入名 `app` 与 `core` 互不相同，因此可以在同一进程里共存。
`suite/boot.py` 只做一件事：在导入任何上游模块之前把这两层挂进 `sys.path`。

> 实测验证：两棵树同进程导入成功，`app.config.ROOT` 与 `core.config.PROJECT_ROOT`
> 各自落在自己的隔离层内，`sys.modules` 里不存在裸 `app` / `core`。

## 三、谁在付钱：两种部署形态

模型凭据有两种来源，**访客填的优先于本站配置的**：

| 形态 | 配置 | 访客体验 |
|---|---|---|
| **BYOK**（默认） | 什么都不配 | 访客必须自己填 API Key，或只用不花钱的功能 |
| **本站出 Key**（公网推荐） | 设 `SUITE_SERVER_LLM_KEY` | 访客打开就能用，无需填写；想用自己的也能填 |

```bash
SUITE_SERVER_LLM_KEY=sk-xxxx          # 本站的模型 Key
SUITE_SERVER_LLM_BASE=https://api.deepseek.com/v1   # 可选，默认 deepseek
SUITE_SERVER_LLM_MODEL=deepseek-chat                # 可选
```

`/api/deployment` 会把当前形态如实告诉前端与访客——**站点用自己的 Key 时，
访客有权知道"这是花站主的钱"**，否则他会在"反正不花我的钱"的预期下大量使用。

### ⚠️ 无鉴权公网部署的成本风险

本站**没有登录、没有鉴权**。一旦配了 `SUITE_SERVER_LLM_KEY` 并公开，
**任何拿到网址的人都能消耗站主的余额，且默认没有上限**。

限流功能已经实现但**默认关闭**（站主选择）。被刷时不必改代码，加一个环境变量即可止血：

```bash
SUITE_RATE_LIMIT=60      # 每个 IP 每分钟最多 60 次，超出返回 429
```

只统计会花钱或会干活的接口（生成、抽取、写作、导入、agent 动作），
静态资源与健康检查不计入——否则打开一次页面就把额度用掉。

两个必须知道的限制：

* 计数只在**内存**里、只在**单进程**内有效，多 worker 时每个 worker 各算一份；
* 反向代理后面若拿不到真实 IP（`X-Forwarded-For` 也没有），会**退化为不限**——
  宁可被刷，也不要把所有正常访客塞进同一个计数桶一起拦住。

### 与上游"借用密钥"的区别（这个区别很重要）

本站的 BYOK 防线（`suite/boot.py`）**封掉了**上游从 `E:\AI\thesis-assistant\.env`
等处**静默借密钥**的行为。而 `SUITE_SERVER_LLM_KEY` 是**站主显式配置**的一行部署设置。

两者不是一回事：**静默借用**是访客不知道、也无法拒绝地从磁盘别处取密钥；
**显式配置**是站主自己决定并写下来的，而且会在接口里如实告诉访客。
封掉前者、保留后者，是有意的。



这是本站**最需要保证正确**的一件事。上游两套代码都有"借用邻居项目 `.env`"的回退逻辑：

* `thesis-agents` 的 `load_settings()`：进程环境变量 > 本项目 `.env` > **邻居项目 `.env`**
* `thesis-topic-helper` 的 `load_settings()`：**邻居项目 `.env`** > 本项目 `.env` > 环境变量

在公网上，这意味着两件绝对不能发生的事：访客不填密钥时站主的密钥被拿去替他付费；
以及密钥被写进日志或错误信息里泄露。

所以本站**一次都不调用上游的 `load_settings()`**：

| 场景 | 做法 |
|---|---|
| 题目生成 | 亲手构造 `core.config.Settings` 注入 `generate_stream(settings, ...)` |
| 写作 / 评估 | 用 `suite/llm.py` 的 `Chat(creds)`，只认显式传入的凭据 |
| 访客没填密钥 | 显式构造 `api_key=""` 的配置 → 上游判定"未配置"→ 走离线模式 |

凭据只存在于**请求局部对象**里，不写 `os.environ`、不写任何全局变量。
环境变量是进程级的，两个访客同时请求会互相覆盖——这正是不能用它的原因。

### 还有一道结构性防线（`suite/boot.py`）

"本站不调用 `load_settings()`"是**靠约定**成立的，不是靠结构。将来任何一条路径
误调一次，就会拿站主机器上的真密钥替访客付费——而且是几十次模型调用的规模。

所以 `boot.prepare()` 会主动把上游的回退**数据**置空（只动两个模块级常量，不碰上游函数体）：

| 档位 | 处理 |
|---|---|
| `os.environ` 里的 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` | 直接删除 |
| `app.config.FALLBACK_ENV_PATHS`（指向 `E:\AI\thesis-assistant\.env` 等） | 换成空元组 |
| `core.config.SIBLING_ENV_FILES` / `SIBLING_MODELS_JSON` | 换成空元组 / 不存在的路径 |

> **为什么不能只把 `LLM_API_KEY` 设成空串**：实测无效。`thesis-agents` 写的是
> `os.environ.get("LLM_API_KEY") or env.get("LLM_API_KEY", "")`——空串为假，
> 于是继续往下读，读到了邻居项目 `.env` 里的**真密钥**。第一版就是这么写的，
> 被 `tools/smoke_byok.py` 当场抓出来。必须删掉环境变量、并清空回退路径元组。

`tools/smoke_byok.py` 用三种方式验证这道防线：

1. 往隔离层放一个带假密钥的兜底 `.env`，调上游 `load_settings()`，必须取不到密钥；
2. 用 **AST** 静态校验 `suite/` 里 12 个模块**没有一个真的调用** `load_settings()`
   （用 AST 而不是 grep，因为在注释里解释"为什么不能调它"会被文本匹配误报成调用）；
3. 从上游源码里提取硬编码的回退路径，证明本机上它们**确实躺着真密钥**——
   也就是说这道防线不是多余的，而是必需的本机开发安全措施。

封印的状态会在 `/api/health` 的 `key_fallback_neutralized` 字段里如实上报，
运行时可见，而不是只写在注释里。

请求头：

```
X-LLM-Key:    访客的 API Key
X-LLM-Base:   接口地址（可选，默认按所选服务商）
X-LLM-Model:  模型名（可选）
```

**接口地址白名单**：公网部署时 `base_url` 由访客提供，服务器会照着它发请求。
默认只放行已知服务商，避免本站被当成任意请求的跳板（SSRF）。
自建或本地部署可设 `SUITE_ALLOW_CUSTOM_BASE_URL=1` 解除限制。

## 四、写作助手的依据分层（2026-10 改版）

### 从"只依据证据库"改成"四层依据 + 可检查的可靠性"

早先这一层有一条**硬闸门**：证据库为空就拒绝生成，连模型都不调用。它防的是编造，
代价是"必须先手工录入资料才能写"。

现在放宽为：**可以依据大模型自身知识与互联网检索到的真实文献来写**。
放宽输入必须补上等价的约束，否则防线就没了。所以不是"打开闸门"，而是
**把"依据"扩成四层，并且每层都能机械检查**：

| 层级 | 来源 | 引用编号 | 怎么验证 |
|---|---|---|---|
| **D 作者文档** | 本次上传的 Word/PDF 正文切出的段落 | `[n]`，从 1 起 | 编号必须在池内；用了材料里的数字却没挂编号会被点名 |
| **A 用户证据** | 访客在「资料获取」录入的文献原文 | `[n]`，接在 D 之后 | 编号必须在本层池内 |
| **B 联网文献** | Crossref / OpenAlex / arXiv 检索到的真实记录 | `[n]`，接在 A 之后 | 编号在池内 + 有真实 DOI 可回查 |
| **C 模型知识** | 大模型训练所得 | **不允许挂编号** | 事后按数字接地复核 |

五条**代码强制**的约束（不靠提示词自觉）：

1. **引用编号必须在池内。** 正文里每个 `[n]` 都必须是 D+A+B 层真实存在的编号；
   越界的记成"编造引用"并点名通报，不静默删掉。
2. **数字必须能在材料里找到。** 两位以上或带小数点的数字需出现在 D+A+B 层原文中
   （年份除外）。这是唯一能机械证伪"这个数从没出现过"的手段。
3. **用了材料却不挂编号，要单独点出来。** 实测真模型最容易犯的错是**把作者上传的文档
   当成"作者自己的话"**：数字照抄、一个 `[n]` 都不挂。那会让覆盖度得出
   "没有任何引用依据"的**反向结论**（作者以为整章都是模型编的，事实正相反）。
   所以这里用数字做指纹机械判定：正文出现了只在某几条材料里才有的数字、却一处编号都没有
   → 标记该章为「用了材料但没挂编号」，并单独换一句结论。
4. **C 层不得挂引用。** 模型知识不许伪装成有出处；挂了编号就按第 1 条被查出越界。
5. **覆盖度如实上报。** 每章回传用了几个 D/A/B 层、编造了几个编号、几处数字找不到依据、
   **文档依据块用了几条 / 总共几条**，并在稿件上方逐章标出。

> 第 5 条最要紧：放宽之后最大的风险不是"写不出来"，而是**作者以为每句都有依据**。
> 所以宁可把话说难听，也不给一个虚假的安心。界面上的结论不粉饰：
> 「同时有你提供/导入的材料与联网文献支撑」/「主要依据联网检索的公开文献（建议核对是否贴合你的论证）」/
> 「依据你导入的文档与你录入的资料」/「仅依据你导入的文档」/「仅依据你提供的资料」/
> 「正文用到了材料里的数据，但没有任何引用编号（内容有依据、但读者无法回查）」/
> 「**没有任何引用依据：正文为模型知识，需自行补证据**」。

### 从 Word / PDF 直接出初稿

「写初稿」阶段最上面就是**拖文件的地方**（`.docx / .pdf / .md / .txt / .html / .csv`，
单文件 ≤ 25 MB，一次最多 10 个）。整条链路：

```
上传 → 解析（不需要 Key）→ 读出写作计划 → 作者确认/修改 → 逐章生成
                              ↓
                     正文切成 D 层依据块，自动带进写作提示词
```

**为什么中间要停一下让作者改**：文档里的要求（多少字、什么结构、投什么期刊）
只有作者自己看得懂。让模型猜一个然后直接生成，作者要么接受一份跑偏的稿子，
要么重来一遍。所以这里只做**解析 + 提议**，把计划摊在界面上（题名 / 章节结构 /
写作要求都**填进输入框**，不是只读展示），改完点「逐章生成」才真的开写。

三个刻意的设计取舍：

* **参考文献段会被剔除**，不进依据池。参考文献表是题录、不是可引用的原文；
  把 60 条题录塞进材料表会让"引用编号在池内"这条检查**看起来**通过（编号确实存在），
  于是一条本该"每处引用都有原文可回查"的检查悄悄退化成"编号存在"。宁可不给。
  （读**写作计划**时给模型看的是整篇文档，包括参考文献——判断"这是论文稿还是任务书"
  需要看全貌。被剔除的只是**依据池**。）
* **材料表按条数截断，不按字数**：最多放 8 条文档块。所以界面显示的是
  "用了几条 / 总共几条"（例如 `6 / 29`），并在超过时给出可操作的提示。
* **没配 Key 也能用**：抽计划要模型，模型不可用时**不报错**，改为按文档自身的
  标题行与章节结构推导一份计划，并在 `plan.source = "local"` 与界面提示里明确标注
  "这份计划是程序推的，不是模型读出来的"。

### 按需单独生成某一部分章节

稿件里**每一章标题旁边都有「重写本章」**。点开可以填这一章要怎么改（可留空），
勾选是否允许联网检索，然后只重写这一章——其余章节原样保留。

关键点：**局部重写不会绕开任何约束**。它与整篇生成共用同一张材料表构造函数、
同一套引用编号校验、同一套数字接地复核，所以"只重写一章"不是"少检查一章"。
结果会**推成一个新版本**（旧版本保留可回退），并在章节上标 `已单独重写`。

这也顺带解决了长文档的问题：材料表只放得下前 8 条依据块，
逐章重写时可以从文档的不同部分取材——这比"一次喂进整篇"更接近作者的真实用法。


### 联网检索为什么是"可靠"的

不是让模型凭记忆报文献，而是**真的去查**：用章节标题与论文题目做检索词，
去四个公开文献库取回记录，只有**同时有题名和足够长真实摘要**的记录才会被采纳。

这是刻意收紧的门槛：只看题名的话，模型看不到内容就只能猜，那正是编造的入口。

* 检索**不需要 API Key**（与本项目的 BYOK 定位一致）
* 只保留有摘要的记录；摘要就是可引用的原文，DOI 可直接回查
* 结果按"有 DOI 优先、其次被引数"排序——被引多通常意味着更可靠
* **某个源限流或超时不影响其它源**，失败信息如实展示
* 检索到的文献会**并入证据库**，下次写作时它们就是 A 层可直接引用

实测（`tools/smoke_websearch.py`）：一次查询从 OpenAlex/Crossref/arXiv 取回
10 条可用记录，摘要 1000+ 字且还原正确（OpenAlex 存的是倒排索引）。

Semantic Scholar 默认关闭：它的匿名额度极小、每次都 429，白等几秒重试。
需要时设 `SUITE_ENABLE_SEMANTIC_SCHOLAR=1` 开启。

### 界面上的开关

「写作」页签有一个**联网检索真实文献作为依据**的复选框（默认开）。
关掉后只能依据 A 层资料 + C 层模型知识，界面会明确提示"本次将完全依据模型自身知识写作"。



### 为什么不用上游的写作链路

上游写作链路**硬依赖一个 RAG 知识库进程**做向量检索，而那个能力由对端
`thesis-assistant` 提供——整个 `thesis-agents` 项目里**没有任何 embedding 实现**
（已 grep 确认）。公网容器里没有对端，照搬的结果是：每章都因"检索不到证据"而拒绝生成，
最终产出空稿加一屏 `writing.needs_source`。

本站的做法是**保留上游的检查器与纪律，换掉检索那一层**：
不再要求先有向量库，而是直接去公开文献库检索真实记录（B 层），
再叠加访客自己录入的资料（A 层）。

**第 3 条数字接地的实现细节**：复用上游的 `check_number_grounding`
（它本来就在 `thesis-agents` 里，且是纯离线检查器），把 A+B 层证据按上游期望的
`meta["writing_evidence"]` 结构喂给它。接入时踩过一个静默失效：上游的章节切分器
**只认单个 `#`**，用 `##` 时这条检查会直接返回空、界面显示"检查通过"。
详见下一节的「坑一」。

## 五、资料获取助手：文件导入

作者手上的资料格式很杂，所以「资料获取」支持**直接拖入文件**，解析成文本后走
同一条抽取链路。**解析不需要 API Key**——它是纯本地处理，访客还没决定用哪个模型时就能用。

| 格式 | 解析方式 | 要点 |
|---|---|---|
| **PDF** | PyMuPDF **逐页**取文本 | 逐页是有意的：页码是学术引用的一部分，证据带 `（第 3 页）` 才能回查 |
| **Word (.docx)** | python-docx | 段落 + **表格**都取（Word 稿子的关键数据常在表里） |
| **Markdown** | 标准库 | 只去行内标记（链接留文字、图片留 alt），保留标题/列表结构 |
| **纯文本** | 标准库 + 编码探测 | UTF-8 / GB18030 / GBK / Big5 依次试探，**并把实际编码报出来** |
| **HTML** | 标准库 HTMLParser | 剥掉 `<script>`/`<style>`，块级标签转成换行 |
| **CSV / TSV** | 标准库 csv | 转成 `列A \| 列B` 的对齐文本，方便模型读表 |

### 三条硬性安全约束

上传是最容易出事的地方，所以这些约束写在代码里而不是文档里：

* **只读、不执行**：纯文本抽取，不渲染、不执行任何内容；
* **限大小限数量**：单文件 25 MB、一次最多 10 个、单文件文本上限 20 万字；
* **不落盘**：解析全程在内存里，访客的文件不写进服务器磁盘。

### 两个刻意的"不假装成功"

1. **扫描版 PDF**。只有位图、没有文本层的 PDF，PyMuPDF 会返回空。这时明确告诉你
   「这份 PDF 共 N 页但取不到任何文字，很可能是扫描版，需要先做 OCR」——
   而不是导入成功、给出一份空证据。**空证据比报错更坏**，因为下游会以为"有依据"。
2. **全部失败时返回 422 而不是 200**。有文件但一个都没读出来，是**真失败**。
   返回 200 会让前端显示"成功，0 条"，那是最误导人的结果。

## 五之二、开题报告：参考文献推荐 + PaperQA2 文献简报

「开题报告」阶段按顺序做三件事，前两件是新增的：

```
① 推荐参考文献  →  ② 用 PaperQA2 出文献简报/问答  →  ③ 导入全文抽成证据（原有）
```

### ① 参考文献推荐（`suite/references.py`）

按选题从 **OpenAlex / Crossref / arXiv** 检索候选，去重合并后按
**文献等级 40% + 被引量 22% + 相关性 18% + 时效 12% + 开放获取 8%** 排序，
输出 10~20 篇。检索、排序、导出、入知识库**都不需要 Key**；
填了 Key 才追加一次可选的模型相关性精排（失败只降级为"没精排"，不影响清单）。

**"文献等级 / 引用量 / 下载量"这三项里，只有一项能真实拿到。** 如实处理如下：

| 排序依据 | 能不能拿到 | 怎么做的 |
|---|---|---|
| **引用量** | ✅ 真实 | OpenAlex `cited_by_count` 等公开字段。是**跨库统计**，与知网的「被引」数字不一致，界面上标「被引（OpenAlex）」 |
| **文献等级** | ⚠️ 目录匹配，不是实测 | 南大 CSSCI / 北大核心**没有公开 API**，所以把刊名与本机内置目录比对；命中才给等级，命中不了写「未收录/未知」，**不猜** |
| **下载量** | ❌ 拿不到 | 知网/万方只在页面上给下载量。OpenAlex 的 `counts_by_year` 是"每年新增被引"，**不是下载量**，改名成下载量就是造假。所以该列一律显示 `—` |

分级这条**踩过两次坑**，现在的规则是：

* 中文刊名走**等值**匹配（归一掉书名号/空格/全角括号）。早先用子串匹配，
  内置目录里的「经济研究」命中了检索结果里的《经济学》（ISSN 2630-4759，非核心），
  它拿到 0.40 等级分后直接排到清单第一名。
* 刊名命中目录、但 **ISSN 与目录记录不符 → 一律不给等级**。这是识破
  "同名仿冒刊"唯一有效的办法（实测检索结果里出现过 ISSN 2630-4686 的《教育研究》，
  与真正 CSSCI 的《教育研究》ISSN 1002-5731 不是同一本）。
* 目录条目里**带 ISSN 的是少数**。实测查了 40 本中文核心刊，绝大多数在 OpenAlex 里
  `issn_l` 就是 `None`（CNKI 侧不向它提交 ISSN），而仿冒刊反而都有 ISSN。
  所以"没有 ISSN"不是可疑信号，"ISSN 对不上"才是——这一点写进了每条的判定依据里。
* 机构仓储（Zenodo、大学知识库）在 OpenAlex 里也是一个"来源"，名字看着像期刊名。
  按 `venue_type` 单独归档为「仓储/未正式发表」，GB/T 导出用 `[D]` 而不是 `[J]`。

**排序不能只按分数截断。** 实测纯截断时高分项全部落在同一本刊、同一年份区间、
常常清一色英文。所以先按档位保底（国内 ≥4、国外 ≥4、跨度 ≥8 年、近 5 年 ≥4），
再按分数补足；保底凑不够时**不硬凑、不报错**，而是在 `notes` 里说明原因。

检索源覆盖这件事也会如实提示：以中文选题检索 OpenAlex/Crossref，返回的中文期刊
**基本全是开放获取的小刊**，知网上主流中文核心刊在这两个库里没有题录。
这不是 bug，而是公开库对中文文献的覆盖就这么大——不说明的话，用户会以为
"推荐里没有核心刊 = 这个选题没有核心文献"，那比不给推荐更糟。

导出三种格式：**GB/T 7714 / BibTeX / Markdown**。缺字段就不写那一项，不补年份、
不编期刊名（与「资料获取」的导出同一口径）。选中的文献可一键存入 RAG 知识库
——存的是**摘要 + 书目**，不是全文，这一点在接口返回里明确写出来。

### ② PaperQA2 文献简报与问答（`suite/paperqa.py` + `tools/pqa_bridge.py`）

选中知识库里的若干篇文献 → 建本地索引 → **提问**（SSE 流式）
或**出简报**（单篇八节 / 多篇对比综述）。

为什么是"包一层"而不是直接用 PaperQA2：

* **它的入口收磁盘目录，本站文献在 SQLite 里**。中间必须有一步"把选中文献物化成
  临时语料目录"。语料按 `<doc_id>/<题名>（年份）.txt` 摆放——一篇一个子目录，
  这样答案里的每条引用都能精确映射回知识库里的哪一篇文献。
* **它的凭据走 litellm 的进程环境变量，本站的凭据在请求头里**。两者直接混用会
  要么把访客的 Key 写进 `os.environ`（并发请求互相覆盖），要么静默去用站点的凭据
  （访客不知情地花钱）。所以凭据**只放进子进程的 env**，父进程一个字都不动。
* **依赖冲突**：PaperQA2 钉 numpy 2.5 / pydantic 2.14，本站跑 2.3 / 2.13，
  同进程加载必有一方静默拿到错版本。所以它住在自己的 `libs-pqa` 里，
  以子进程 + JSONL 通信。本机 `E:\AI\thesis-assistant\libs-pqa` 已有完整安装
  （1.19 GB），**用路径引用而不是复制**（`SUITE_PQA_LIBS`）。

中文与 CNKI PDF 有三个坑，结论来自 `thesis-assistant` 的实测，这里照搬：

1. **中文长文会被判为"不是文本文档"**。PaperQA2 的 `maybe_is_text()` 只接受每字符熵
   在 2.5~8.0 之间的文本；这个上限是按字母文字校准的（英文上界 `log2(25)≈4.7`），
   中文有约 1210 个相异字符、上界 `log2(1210)≈10.24`，所以**任何超过约 5000 字的
   中文论文都会被拒**。必须设 `parsing.disable_doc_valid_check=True`。
2. **默认解析器 pypdf 读不了 CNKI 的 PDF**（报 malformed MediaBox 且抽不出文字），
   必须装 `paper-qa-pymupdf`。
3. **智能体路径在当前依赖组合下是坏的**：`fhlmi 1.0.7` 把 litellm 垫片定义成只收
   关键字参数，而 `aviary` 的 `ToolSelector` 把模型名作为第一个位置参数绑定进去，
   于是任何走 agent 的调用都抛 `TypeError: _acompletion() takes 0 positional
   arguments but 1 was given`。绕开办法是走 `Docs.aquery` 手动 API。

向量模型用 `BAAI/bge-small-zh-v1.5`（本地，512 维）。本机访问不了 huggingface.co，
所以 `SENTENCE_TRANSFORMERS_HOME` **直接指向已经下好的那份缓存**
（`E:\AI\thesis-assistant\.tmp\st_home`，91.9 MB），不重下。

界面上的三个按钮分别是「建立索引」「提问」「出简报」，索引**单独建**是有意的：
建索引要对每篇文献调一次模型，把它和提问绑在一起会让第一次提问变成三分钟的空白等待。
索引建好即缓存，之后每次提问约 10~25 秒。

> 本机自用想省掉每次粘贴 Key，可以设
> `SUITE_PQA_LOCAL_KEY_FILE=E:\AI\thesis-assistant\.env`。
> 这是**显式开关**，不设就完全不借任何密钥——与 `suite/boot.py` 封掉"静默借用邻居
> 项目 .env"的那道防线一致。它只在**访客没填 Key 且站点也没配 Key** 时才生效。

### ③ 生成开题报告：三层依据 + 导入任务书（`suite/api/proposal.py`）

阶段 3 把资料写成开题报告。依据来源与「写初稿」**同一套口径**，四层里前三层可用：

| 层 | 来源 | 引用编号 | 能不能关 |
|---|---|---|---|
| **K 知识库** | 本地上传的 PDF/Word 全文、参考文献推荐存进去的摘要 | `[n]` | 能（开关） |
| **A 用户证据** | 会话里录入的证据 | `[n]` | 随会话 |
| **B 联网检索** | Crossref / OpenAlex / arXiv 的真实记录 | `[n]`，带 DOI | 能（开关） |
| **C 模型知识** | 大模型自身训练所得 | **无编号** | **不能** |

C 层是允许存在的（用户明确要"也可以依据大模型本身的知识"），但它有三个不可让步的
约束：**不许挂引用编号**（挂了就按越界通报为编造引用）、**不许编数字**（数字接地
复核会点名）、**必须如实计入覆盖度**。第三条尤其要紧——放宽依据来源后最大的风险
不是"写不出来"，而是作者以为每一句都有出处。所以成稿页面会把"本次依据"
（哪几层开、哪几层关）与**分层计数**一起印出来。

参考文献仍然**不由模型生成**：正文引用了谁，列表里才出现谁。

**材料表的额度分配有个容易踩的坑**：知识库检索一次很容易返回 6 条，按"先到先得"
分配的话 B 层（唯一带 DOI、能点回原文的一层）会被挤到一条都进不来。所以
`_build_material` 是**先给 B 层留够额度，剩下的才给 A 与 D**。

**导入任务书 / 模板（`POST /api/proposal/import-plan`）**一次做三件事，都是
"用户不该被要求做第二遍"的事：解析文件（本地，不需要 Key）→ 正文切块**存进知识库**
（于是生成时自动成为 K 层依据，不必再单独导入一次）→ 从文档里读出**框架与要求**。

第三步刻意**不用模型**：开题报告的框架是固定七节的闭集，关键词匹配就足够可靠，
既省一次调用，也让没配 Key 的用户不会掉进"计划是程序猜的"那种降级态。
识别不出框架时返回**空表**而不硬凑——让调用方退回默认七节，比返回一个只认出一半、
顺序还乱的框架好（后者会让用户以为"文档里的结构就是这样"）。

实测（`tools/smoke_proposal_flow.py`，30 项断言 + `tools/live_full.py` 真实链路）：
七个小节全部识别、写作要求被摘出、正文入库后能被检索到；
两层都开时材料分层为 `{'K 知识库': 6, 'B 联网检索': 6}`，
引用 11 条、**编造引用 0 条**、找不到依据的数字 3 处被点名。

**联网检索的健壮性**（与 `suite/references.py` 同一套做法）：某个源返回 429
（OpenAlex 无 Key 时免费额度按 IP 共享、耗尽当天不可用）时，**本次不再重试那个源**。
早先每个检索词都重试一遍，3 个检索词里有 3 次是在明知会失败的情况下白等超时——
一次推荐从 15 秒拖到 2 分钟以上，结果**一条都没多**。判据是"这个源现在用不了"
（限流/连不上/超时）才拉黑：arXiv 对中文选题会**正常返回 0 条**，那不是故障，
不能被当成故障。

### 「参考文献与知识库」阶段：论文RAG知识库

阶段 2 的卡片顺序是：推荐参考文献 → 推荐清单 → 口径与限制 →
**论文RAG知识库** → 下一步入口。

**论文RAG知识库**这一张卡片就是本阶段的知识库本体，四段结构按"使用顺序"排：

```
① 把资料放进知识库   PDF / Word / 整目录拖入；本地解析；**整篇入库**
② 文档库             一篇文件 = 一篇文献（列出字数/片段/页数/来源/时间）
                     可勾选、可删除选中、可清空全部
③ 建立索引           总结 / 对比 / 问答 的公共前置（PaperQA2，每篇调一次模型）
④ 用这个知识库做事     文档检索 | 论文总结 | 跨文档对比 | 问答
```

四个功能是从本机的 `E:\AI\thesis-assistant`（论文RAG知识库助手）搬进来的，
但**共用站点这一个知识库**，不是两套：

| 页签 | 引擎 | 要不要 Key | 说明 |
|---|---|---|---|
| **文档检索** | 本地 jieba + SQLite FTS5 | ❌ | 放第一个是刻意的：**不花钱、即时返回**，最常用 |
| **论文总结** | PaperQA2（勾选 1 篇，读**整篇**） | ✅ | 八个小节，用「关注焦点」 |
| **跨文档对比** | PaperQA2（勾选 ≥2 篇） | ✅ | 共识/分歧/方法差异/演进脉络/研究空白 |
| **问答** | PaperQA2（SSE 流式） | ✅ | 逐字上屏 + 可回查的引用来源 |

#### 存储模型：整篇入库 + 页映射（2026-10 改版）

这一版把知识库从"只存切块"改成"整篇 + 索引"。改动原因都是实测出来的：

| 问题 | 实测证据 | 现在 |
|---|---|---|
| **取回文本被污染** | 早先只存切块，取回时把块间 80 字重叠又拼了一遍：**1330 字 → 1494 字**，关键句 72 次 → 80 次 | `docs.text` 原样存整篇，`get_document` 直接读它，**取回 == 原文** |
| **一篇论文裂成几十条** | PDF 逐页入库，一篇 63 页的论文在文档库里是 **63 条记录** | 一篇文件 = 一篇文献（迁移后实测 **62 → 2 条**） |
| **页码会丢** | 整篇入库后若不记页映射，引用只能到"第几段" | 入库时算出「每页在全文中的字符区间」，把页码记到**每个切块**上 |
| **跨页块只报起始页** | 一个 600 字的块从第 7 页跨到第 8 页，写"第 7 页"等于说错 | 记 `page_end`，引用写成**「第 7–8 页」** |
| **简报吃的是片段** | 早先物化语料来自"切块拼回来的文本"，且单篇上限 40000 字 | 语料来自整篇；上限抬到 200000（PaperQA2 本就按块检索，不需要限制上下文） |

> 那句"整本专著塞进去一次提问的上下文会爆"是**错的理由**：PaperQA2 先按块建索引、
> 再按问题检索相关片段进上下文，从不把整篇塞进一次提问。40000 的真实后果只是
> 把一篇 47000 字的论文截掉 7000 字。

老库用 `tools/migrate_kb.py` 升级（幂等，**自动先备份到 `data/backups/`**）：

```powershell
python tools\migrate_kb.py --dry-run    # 只看计划
python tools\migrate_kb.py              # 补全文 + 合并按页拆开的记录
```

#### 检索模型：关键词 + 语义向量 → RRF 融合（`suite/embedding.py`）

**旧行为的问题**：检索是纯关键词（jieba + SQLite FTS5）。它能精确命中字面，
但查「组织支持」不会命中讲「职业倦怠」的那一段——而这两件事在文献里常常是同一段话。
这是知识库质量的天花板。

**现在的做法**：两路召回，用 RRF 融合。

```
查询 ──┬─→ FTS5（jieba 分词，BM25）        ──┐
       └─→ bge-small-zh-v1.5（512 维余弦）  ──┴─→ RRF 融合 → top-k
```

| 决策 | 选择 | 理由 |
|---|---|---|
| 向量模型 | `BAAI/bge-small-zh-v1.5`（91 MB，本机已缓存） | 检索是**高频**路径，每次查询都要编码一次。bge-m3/bge-large 会把单次检索从 80ms 拉到 300ms+，在这批语料上召回差异很小 |
| 融合方式 | **RRF**（`score = Σ 1/(60+rank)`） | BM25 与余弦**量纲完全不同**，加权平均要先归一化，而归一化方式直接决定谁主导排序，没有客观依据。RRF 只看名次，对量纲免疫 |
| 向量存放 | `chunks.vec`（float32 裸字节） | 与文本同表同事务，删除/重建天然一致，不需要另建向量库 |
| 在哪里算 | **常驻子进程**（`tools/embed_server.py`） | 向量依赖在 `libs-pqa`（numpy 2.5 / pydantic 2.14），主进程是 numpy 2.3 / pydantic 2.13。同进程加载必有一方静默拿到错版本——与 PaperQA2 走子进程同一个原因 |

**冷启动与降级**（这一段是这个功能最容易做错的地方）：

- `import torch` 约 30 秒、加载模型约 7 秒，所以进程**常驻**、启动时**后台预热**；
  预热期间检索照常工作（纯关键词），完成后自动升级，**请求永远不会等它**
- 预热后单次查询约 **15ms**（实测 13~16ms），首次查询会多 ~700ms（建向量矩阵缓存）
- 公网容器里既没有 `libs-pqa` 也没有模型：那条路上 `search()` 仍返回结果，
  只是模式为 `keyword`。**`/api/kb/embed/status` 会如实报告三种状态**
  （未启用 / 预热中 / 已就绪），界面据此显示，绝不含糊其辞

**RRF 的一个真实缺陷，以及我们怎么补的**：当两路列表恰好互为逆序时，每个条目的
名次之和相同，RRF 分会**完全相等**。实测题「教师心理压力」就是这样——关键词把
"量表信效度"排第一、向量把"职业倦怠"排第一，融合后并列 `0.0325`，谁第一取决于
排序算法的稳定性。余弦本身是分得开的（0.650 vs 0.563），信息没丢，是被 RRF 抹平了。
所以加了一条**确定的**并列规则：**RRF 分相同时，向量名次更靠前者优先**。
不是为了偏向向量，而是因为"加向量路"的整个目的就是让语义参与排序；并列时退回关键词，等于白加。

**向量补齐**：老数据入库时模型可能还没就绪，那些块的 `vec` 为 NULL。用
`POST /api/kb/embed/backfill`（或界面上的「补齐 N 个片段的向量」）补，**幂等**，
只处理 NULL。实测 111 个片段 5.2 秒补完，本地编码不花钱。

```powershell
python tools\smoke_hybrid_search.py          # 含模型预热，约 25 秒
python tools\smoke_hybrid_search.py --fast   # 只跑 RRF / 降级等纯逻辑
```

#### 批量导入：由前端分批，不设"一次 10 个"的硬上限

后端单批上限 25 个文件（`kb.upload` 的 `MAX_FILES_PER_BATCH`），但**这不是总数上限**：
前端把用户选的任意多个文件按每批 8 个依次上传，进度按"已完成 / 总数"走。

- 一次拖 200 篇也能进；某一批失败只把那一批记为失败，**不中断后面的批次**
- 「选择整个文件夹」用 `webkitdirectory` 把整个目录交上来，并按后缀筛掉非文献文件
- 单批累计超过 120 MB 会拒绝该批（提示拆小），避免一次把几百 MB 读进内存

#### 批量删除

- 「删除选中」→ `POST /api/kb/delete-batch`，**一个事务里删完**；不存在的 id 归入
  `missing` 而不是报错（删不存在的条目不算失败，但要让调用方知道）
- 「清空整个知识库」要求**手输「删除」二字**——库里可能是几个月的入库成果
- 单篇删除按钮放在勾选区的 `<label>` **外面**：`<label>` 里点任何元素都会连带切换
  复选框，于是"想删一篇"会变成"又勾上一遍"。每行因此是 `div`，勾选区自己套 `label`

**为什么不再单独复制一套助手的索引**：助手（`thesis-assistant`）有自己的
`inbox/` 与 `data/index/`，而阶段 3「生成开题报告」与 PaperQA2 简报读的是站点的
`suite/rag.py`。如果在这里嵌一套、那边留一套，用户会发现自己入的 PDF
**开题报告检索不到**——那是最难解释的一类故障。所以这里共用同一个库：
入一次，四个功能与开题报告都可用。

**入库入口与四个功能放在同一张卡片里**，而不是另起一张：两者是同一件事的两半
（没有资料，检索/总结/对比/问答都无从谈起），分开放会让用户在一张标题写着
「论文RAG知识库」的卡片里**找不到怎么放资料**。

**工作顺序：先入库，再按整篇看简报。** 文档库现在一行就是一篇完整文献，
所以"选中 1 篇 → 论文总结"是让模型读**整篇**再写八节简报；
"选中 ≥2 篇 → 跨文档对比"读的也是各自整篇。检索则相反——它按切块命中，
所以给的是"最小可引用的那一段"，并带页码便于回查。两者不矛盾：
**入库整篇（保真）、检索切片（精准）、简报/对比用整篇（完整）。**

另外：**不只看扩展名**。文件头优先——把 `.pdf` 改名成 `.txt` 会被按 PDF 正确识别；
而 `.xlsx`/`.pptx`（zip 容器）会被明确拒绝并说明原因，而不是拿文本解析器啃出乱码。

实测（`tools/smoke_import.py`，32 项断言）：PDF 两页逐页拆分、扫描版被识别、
DOCX 表格未丢、Markdown 链接处理、GBK 正确解码、HTML 剥脚本、伪造扩展名纠正、
空文件/超大文件/不支持类型都被明确拒绝。

全链路实测（`tools/live_import_chain.py`，真实模型）：拖入一份 2 页 PDF →
逐页拆成 2 段（带页码）→ 抽取 12 条原文片段（**0 条被逐字校验丢弃**）→
写作 2238 字、引用导入的证据、**0 编造引用、0 无依据数字**。



评估能力是四个助手里**唯一完全不依赖模型就有价值**的：53 个检查器全部
`needs_llm=False`、不联网、不花钱。但接入它踩了两个静默失效的坑：


**坑一：章节标题的层级。** 上游 `split_by_sections` 的行为是
**在第一个 `#` 行处切第一刀，而 `##` 不算标题（算正文）**。
这个细节让「数字必须有依据」这条检查有三种失败方式，全部实测踩过：

| 稿件的标题形式 | 结果 |
|---|---|
| 全用 `##` | 一章都切不出 → 检查直接返回空，界面显示"检查通过" |
| 归一化成"每行都 `#`"，但首行是论文题目 | 切出来的第一"章"是**题目**，第 1 章被它吞进正文，检查只覆盖题目那一行 |
| 归一化成"第一个 `#`、其余 `##`" | `##` 又变回正文，切得更少 |

正确做法：**把每一章都还原成 `#`，同时把论文题目从待检文本里摘掉**——
题目本来就不含需要检查的正文，摘掉之后第一个 `#` 天然就是「第1章」。
实现在 `suite/api/review.py` 的 `normalize_headings()` + `strip_leading_title()`，
并且**两个入口分支都必须走这一步**（草稿分支早先跳过了归一化，是同一类静默失效）。

> 这一条反复踩的根源是：诊断口径与实现口径不一致。我在排查时自己写正则统计"正文数字"，
> 结果把「教龄 11～15 年」这种**区间**拆出了个 `10`，据此误判"检查器失效"；
> 而检查器用的是 `fact_numbers()`，它会正确剔除区间。**诊断必须复用实现里的函数，
> 不能另写一份**——否则会得出比没有诊断更坏的结论。

**坑二：误告造假与误告真实，两个方向都要防。**

* 解析器会把「参考文献」这个章节标题也当成一条条目，拿去检索必然 `not_found`，
  报告里就多出一条"查无此文"的**假警报**。误告造假比漏报严重得多，
  所以按上游的 `lookupable` + `title_quality == "high"` 两道判据过滤，
  并把跳过数量如实告诉访客。
* 反方向：上游在 DOI 查不到时**退回按标题做词级相似度检索**，
  而这个相似度会高得离谱——上游作者实测一条完全编造的标题以 **0.93**
  命中了一篇真实存在的论文。也就是说**编造的文献可能被盖章成"真实"**。
  本站因此对"没有 DOI、只能靠标题"的条目把 `confirmed` 降级为 `weak_match`。

结论是本站的核验功能保证的是**"题录能不能对上真实记录"**，
**不保证文献结论为真**。界面上也照这个口径说明。

## 六、界面：连续工作流（布局参考 ThesisMind）

站点最初是**四个并列页签**（题目生成 / 资料获取 / 写作 / 评估）。这有个真实问题：
它把一件事拆成了四个工具，用户看不出"下一步该做什么"，做完一步会停在原地。

现在改成**连续工作流**：左侧五个阶段，右侧是当前阶段的工作台，数据跨阶段留着。

| 阶段 | 做什么 | 对应能力 |
|---|---|---|
| ① 定题目 | 先有一个能写下去的题 | 题目生成（离线也能用） |
| ② 开题报告 | 把文献与依据找齐 | 资料获取（拖文件 / 联网核验） |
| ③ 写初稿 | 逐章生成正文 | 写作（三层依据） |
| ④ 修改与评估 | 跑检查、出意见书 | 评估（53 个检查器） |
| ⑤ 答辩材料 | 答辩稿与演示提纲 | *尚未实现，界面上明确标为「即将上线」* |

### 布局与设计系统的参考来源

布局参考 <https://thesismindai.com/>（ThesisMind · 论心 · 写作助手）。
它的公开前端产物里有两条关键信息，本次改造就是照它做的：

* **信息架构**：它把论文写作当成"一个学期的事"，官方表述是
  「任务书、开题、初稿、修改、查重、答辩，每一步都接着上一步做」。
  这确认了"连续阶段 + 数据跨阶段保留"的方向，而不是并列工具。
  它还有一句与本项目取向完全一致：**「不编造任何一条文献」**。
* **设计系统**（从它的 CSS 变量里实测读出，不是猜的）：shadcn/ui 令牌体系，
  **主色是中性灰**（`oklch(20.5% 0 0)`，无色相）、侧栏 **300px**、
  `--radius: .625rem`，以及一套**完整重定义的暗色模式**（24 个变量，不是简单反色）。

这些令牌原样搬进了 `web/theme.css`，以 `--tm-` 前缀命名（避免与原有的
`--bg/--ink` 冲突）：

```
--tm-primary / --tm-muted / --tm-border / --tm-ring
--tm-success / --tm-warning / --tm-destructive / --tm-link
--sidebar-w: 300px
```

### 三个实现取舍

1. **阶段不做硬性关卡**。作者手上常常已经有初稿，直接进「修改与评估」是完全正常的
   用法。把阶段做成必须按顺序通过只会挡住真实流程，所以阶段完成状态**只是提示**，
   不拦人。侧栏的阶段圆点会显示已完成 / 当前 / 未开始。
2. **每个阶段底部有"下一步"出口**。阶段化最常见的失败是"看着像流程、用起来还是
   各干各的"——所以每个工作区底部都注入了一个明确的下一步按钮。按钮由 JS 按
   `STAGES` 定义注入，而不是写死在 HTML 里：流程定义只有一处，改了顺序不会忘记改按钮。
3. **stage 与 panel 是两个概念**。stage 是给用户看的阶段，panel 是承载界面的容器
   （`p-topics` / `p-gather` / …）。分开是因为一个阶段将来可能对应多个 panel，
   而这次改造要**保住后端与四个功能块的既有逻辑不动**，只换导航与布局。

### 暗色模式

照 ThesisMind 的做法：`localStorage` 键 `thesis-theme`，取值 `light` / `dark` / `system`；
**"跟随系统" = 按当前小时判断（19:00–07:00 视为暗色），与操作系统设置无关**——
这是参考站的既定行为，我重新抓过它的页面核实（它的内联脚本就是
`p === "system" && (h >= 19 || h < 7)`，整页 HTML 里 `prefers-color-scheme` 一次都没出现）。

`<head>` 里有一段**内联脚本先于样式执行**，避免暗色用户看到亮色闪一下。

> 这个判定同时存在于 `index.html`（防闪白脚本）与 `app.js`（`Theme.systemIsDark`），
> **两处必须一致**，否则表现为"首屏闪一下再变色"。`tools/smoke_workflow.py` 把这个
> 不变量固化成测试了。过程中踩过一次：`app.js` 里曾挂 `prefers-color-scheme` 监听，
> 与按小时的判定语义冲突（白天系统是暗色时，内联脚本给亮色、监听一触发又翻暗）。

### 阶段按钮：HTML 与 JS 的关系

五个阶段按钮在 `index.html` 里**静态写了一份**，`app.js` 的 `buildStages()` 会优先
复用它们（找不到才自行渲染）。静态那份是**boot 之前的骨架**，目的是让首屏侧栏
立刻可点、不出现空白。

代价是**文案有两处**：改阶段名时要同时改 `index.html` 与 `app.js` 的 `STAGES`。
之所以保留这个重复，是因为它换来的是"首屏无空白且无跳变"；如果哪天觉得不值得，
把 `index.html` 里那五个按钮清空即可——`buildStages()` 会自己渲染。

### 让它"随时打开就有"（常驻服务）

不想每次手动敲命令，用 `service.ps1` 把它做成常驻：

```powershell
cd E:\AI\thesis-suite
.\service.ps1 install     # 装登录自启并立即启动
.\service.ps1 status      # 看状态（含健康检查与密钥封印状态）
.\service.ps1 stop        # 停止
.\service.ps1 restart     # 重启
.\service.ps1 uninstall   # 卸载自启并停止
```

装好之后，**每次登录 Windows 站点就自动在 8848 端口待命**，浏览器打开
<http://127.0.0.1:8848/> 即可，不用再开终端。

> **自启端口曾经对不上**，这一段值得记下来。`service.ps1` 的默认端口是 **8878**
> （避开 8848 被别的本地服务占用的情况），而启动项走的是 `start_background.cmd`。
> 早先那个脚本把 `SUITE_PORT` 也默认成 8878，于是**登录后守护的是 8878，
> 而书签里打开的是 8848**——8848 那份没有任何看门狗，崩了就一直"无法访问"，
> 看起来像"站点自己消失"。现在 `start_background.cmd` 的默认值钉成 **8848**，
> 与用户实际打开的地址一致；`service.ps1` 自己的默认仍是 8878，两者互不影响。
> 想换端口就在启动项里设 `SUITE_PORT`，它会覆盖这个默认值。

如果 `install` 报"两种自启方式都被当前权限拒绝"（受限会话、组策略、或非管理员环境），
在**管理员 PowerShell** 里粘这一行即可，效果相同：

```powershell
Copy-Item 'E:\AI\thesis-suite\start_background.cmd' ([Environment]::GetFolderPath('Startup') + '\ThesisSuite.cmd')
```

三点值得说明：

* **自启有两套兜底**。优先用计划任务；被权限拒绝就改用"启动文件夹"（不需要管理员）。
  两套都被拒时脚本不会失败，而是**打印一条可直接复制执行的命令**。
* **`start_background.cmd` 是幂等的**（内部用 `service.ps1 start -IfIdle`）。
  登录自启和手动启动各跑一次，不会起两个进程抢端口。
* **只监听本机**。要让同一局域网的其他设备（手机、平板）也能访问，用
  `.\service.ps1 start -Host_ 0.0.0.0`，然后用 `http://<本机IP>:8848/`。
  注意那等于把服务暴露给局域网，而本站**没有任何访问鉴权**——只在可信网络里这么做。
* **不在本机时不适用**。这是本机常驻方案，不是公网部署；公网见第八节。

日志在 `logs/service.out.log`（UTF-8，中文可读，由 Python 侧自己写）。

`-RedirectStandardOutput`，.NET 会等子进程退出才返回，而常驻服务永远不退出——
"启动"命令就会永远挂住。实测踩过两次，细节写在 `suite/__main__.py` 的 `_log_config` 里。

### 看门狗：服务崩了会自己起来，代码改了会自己重启

`watch.ps1` 常驻后台，做两件事：

| 职责 | 参数 | 说明 |
|---|---|---|
| **健康检查** | 15 秒一轮，**1 次失败就重启** | 崩溃到恢复实测 **14 秒**（旧版是 60s × 3 次，最长 3 分钟） |
| **源码自动更新** | 监听 `suite/**` 与 `tools/**` 的 `.py` | 改完后端代码**不用再敲命令重启**，看门狗自己换到新版本（实测 18 秒生效） |

```powershell
.\start_background.cmd        # 启动看门狗（推荐；它会拉起服务并持续守护）
```

**为什么阈值从 3 次降到 1 次**：连续 3 次 × 60 秒意味着最长 **3 分钟**打不开，
而"多等两轮"省下的只是极少数网络抖动造成的误重启——服务真的挂了才是常见情形。
15 秒一轮、1 次即重启，把最坏恢复时间压到十几秒。

**为什么重启用"15 秒一轮"而不是秒级轮询**：检查本身要发一次 HTTP 请求，
秒级轮询在高频读盘时反而会抢占 CPU，而 15 秒已经是人感知不到的分界。

**前端不用重启**：`web/*.js|css|html` 是每次请求从磁盘读的，改完刷新浏览器就是最新。
所以源码指纹**故意只统计 `.py`**——把前端算进去会导致"改一行 CSS 就重启后端"，
白白中断正在跑的生成任务（一次文献简报要 90~155 秒）。

实测验证（8848 端口，生产参数 15s × 1 次）：

```
[05:52:38] 杀掉站点进程
[05:52:52] 服务已就绪              ← 14 秒自愈
[05:53:13] 检测到后端源码变化（5359443012D0C4F5 → 1255BF5CE74A8F35），自动重启服务以加载新代码
[05:53:14] 已停止 → 重新启动 → 健康
```

> 要完全停掉：先 `.\service.ps1 stop`，再结束 `watch.ps1` 进程。
> 只看门狗停、服务不停，或者反过来，都会让它下一轮又起来。

#### 一个必须说清的限制：进程会被"连坐"回收

实测：助手每次工具调用都把子进程放进一个**作业对象（Job Object）**，调用结束或
后台任务被取消时整个作业被关闭，里面的进程**全部被杀**——包括站点和看门狗。
所以"站点隔一阵就没了"通常不是它自己崩了，是被连坐回收。

可用的三条出路都试过了：

| 方案 | 结果 |
|---|---|
| `schtasks` / `Register-ScheduledTask` | **拒绝访问**（沙箱不允许注册计划任务） |
| `CREATE_BREAKAWAY_FROM_JOB` 脱离作业（`tools/detach_watchdog.ps1`） | **Access denied**（作业不允许脱离） |
| WMI `Win32_Process.Create`（进程挂到 WmiPrvSE 下，不在作业里） | **拒绝访问** |

因此真实可用的持久化只有一条：**登录自启**。启动文件夹里的 `ThesisSuite.cmd`
在每次登录时调用 `start_background.cmd` → `watch.ps1`。它运行在**你自己的会话**里，
不受助手作业对象影响，重启电脑或重新登录后都会自动恢复。

如果哪天打开页面发现打不开，按代价从低到高：

1. 等一下 15 秒——看门狗可能正在拉；
2. 双击仓库里的 `启动网站.cmd`（**一次点击，不用敲命令**）；
3. 注销再登录一次——启动项会把它重新拉起来。


### 打不开的时候：先跑一键诊断

```powershell
.\diagnose.ps1
```

一次列清楚：文件是否齐全、依赖能否导入、端口有没有在听、服务健康检查、
看门狗是否存活、登录自启有没有装，最后直接告诉你怎么启动 / 恢复。

### 本机常驻做了哪些验证、哪些没做

**已实测**（在开发机上）：

| 验证项 | 结果 |
|---|---|
| 服务启动 | 1.6 秒内就绪，`/api/health` 返回 200 |
| 连续运行 | 同一会话内稳定 90 秒，运行时长单调递增（12→28→43→58→73→88s），说明是同一进程、看门狗未误重启 |
| 崩溃自愈 | 杀掉服务后**约 6 秒**自动恢复，`logs/watchdog.log` 有完整记录 |
| 幂等 | 重复调用不产生第二个进程（`-IfIdle`） |
| 启动器 | `start_background.cmd` **0 秒返回**，不阻塞调用方 |
| 日志编码 | UTF-8，中文可读（Python 侧自己写，不经 PowerShell 管道） |
| 脚本编码 | `.cmd` 纯 ASCII、`.ps1` 带 BOM（`tools/check_encodings.py` 强制） |
| 启动项 | 用户启动文件夹已写入 `ThesisSuite.cmd` |

**未验证**（开发环境无法验证，需要你在真实登录环境里确认）：

* **登录后是否真的自动起来。** 我这边每次命令会话结束，子进程都会被运行环境回收，
  所以无法演示"跨越 shell 退出仍然存活"。启动项本身已正确安装，请**下次登录后**
  打开 <http://127.0.0.1:8878/> 确认；或随时跑 `.\diagnose.ps1` 看「登录自启」一节。
* **长期稳定性。** 只观察到分钟级；按设计看门狗每分钟检查、连续 3 次失败才重启，
  最长 3 分钟自愈。

如果登录后打不开，先跑 `.\diagnose.ps1`，它会直接告诉你缺哪一环。

### Windows 脚本的编码约束（改脚本前必读）

`tools/check_encodings.py` 把这条固化了。改完脚本跑一下：

```powershell
python tools\check_encodings.py
```

* **`.cmd` / `.bat` 必须纯 ASCII。** `cmd.exe` 按代码页探测解码，UTF-8 中文注释会让它
  吃掉 `rem` 前缀，把注释当命令执行（实测报 `'双击即可启动本机服务' is not recognized…`）。
* **`.ps1` 允许中文，但必须有 UTF-8 BOM。** Windows PowerShell 5.1 对没有 BOM 的脚本
  按 ANSI/GBK 解码，中文注释被解坏后**直接语法错误**，而且报错位置指向参数块，
  完全看不出是编码问题（实测报 `Missing expression after ','`）。

> ⚠️ 用编辑器/脚本改这两个 `.ps1` 之后**务必确认 BOM 还在**——
> 大多数写入工具默认不保留 BOM，这个坑在开发过程中反复踩过三次。
> `check_encodings.py` 就是为它写的。

## 七、测试

```powershell
$env:PYTHONPATH = "E:\AI\thesis-suite;E:\AI\aigc-reducer\libs;E:\AI\thesis-assistant\libs"
$env:PYTHONUTF8 = "1"

python tools\smoke_suite.py         # 端到端：装配 / 离线出题 / 闸门 / 检查器 / 会话 / 前端
python tools\smoke_writing_import.py # 新增：Word/PDF 导入出初稿 + 单章重写（53 项，假模型，不花钱）
python tools\smoke_frontend.py      # 前端资产与写作接口字段
python tools\smoke_gather.py        # 资料获取：50 项断言（含真实 Crossref 核验）
python tools\smoke_references.py    # 参考文献推荐：分级不误判 / 配比生效 / 导出条数与字段（不花钱）
python tools\smoke_paperqa.py       # PaperQA2 链路：物化、凭据隔离、边界（离线，不花钱）
python tools\smoke_paperqa.py --live --key-file E:\AI\thesis-assistant\.env   # 真建索引并提问（会花钱）
python tools\smoke_byok.py          # BYOK 防线：服务器密钥不可被借用（含 AST 静态校验）
python tools\smoke_container.py     # 容器形态：干净环境 + suite/vendor 同级摆放
python tools\check_requirements.py  # 依赖对账：requirements.txt 是否覆盖源码的真实 import
python tools\live_chain.py          # 真实模型跑完整链路（会花钱），密钥从既有项目 .env 读
python tools\live_writing_import.py # 真实模型跑"导入 Word → 初稿 → 单章重写"（会花钱，规模很小）
```

`smoke_references.py` 里有几条断言值得单独说，因为它们对应的都是**实际踩过的坑**：

* 内置核心目录里原本有「经济研究」，而检索结果里出现了《经济学》（ISSN 2630-4759，
  非核心）。子串匹配把后者判成了 CSSCI，它的 0.40 等级分随即把它送上清单第一名。
  现在中文刊名走**等值**匹配，且刊名命中目录但 ISSN 对不上时**一律不给等级**。
* 下载量在任何公开库里都拿不到。脚本断言清单里每条的这个字段**必须是 `None`**——
  防止日后有人填个估计值进来，把"如实留空"变成"看起来有数据"。
* 配比（国内外都有、时间跨度 ≥ 8 年、近 5 年 ≥ 4 篇）不是装饰：纯按分数截断时
  高分项会全部落在同一本刊、同一年份区间。

`smoke_paperqa.py` **默认离线**（依赖、凭据、物化、边界四类断言，不联网不花钱），
加 `--live` 才真的建索引并提一个问题。它把知识库与索引都重定向到
`.tmp\smoke_pqa\` 下的沙箱，跑完即弃——这个脚本被误当成生产工具一次的代价是
用户丢资料，不值得冒这个险。它同时断言两件容易被写错的事：

* 访客的 Key **只进子进程的 env**，绝不写进父进程 `os.environ`
  （写进去就是并发互相覆盖 + 可能被别的库读到）。
* 语料目录里只有 `.txt`，不能混进签名文件——签名文件曾经放在语料目录下，
  结果 PaperQA2 把它当成第 4 篇文档索引了进去。

`smoke_writing_import.py` 的手法值得单独说一句：它把
`suite.api.writing.llm_mod.Chat` **换成一个假客户端**，于是接口层（解析、材料表、
引用校验、数字接地、版本推进）跑的全是真代码，只有"模型返回什么"是假的。
这样验证的是**本站自己的逻辑**，而不是模型的心情——也正因为如此，它能断言
"参考文献没进材料表""用了材料却没挂编号会被查出来"这类模型随机性下测不了的东西。
真模型那一半由 `live_writing_import.py` 补上（默认会在没有 Key 时自动跳过）。

其中 `smoke_container.py` 是最接近"公网会怎样"的一个。它在开发机上模拟容器环境：

* 把 `suite` 与 `vendor` 复制到一个裸目录**同级摆放**（等价于镜像里的 `/app`）；
* 用 `python -S -I` 起子进程——**不读 site-packages、不继承 `PYTHONPATH`**，
  依赖只来自显式指定的目录（等价于容器里 pip 装出来的那份）；
* 把 `E:\AI\thesis-assistant`、`E:\AI\aigc-reducer`、`E:\AI\thesis-agents`
  三个 Windows 绝对路径**打桩成不存在**（等价于 Linux 容器里的情形）；

然后验证离线出题、53 个检查器（含数字接地）、FastAPI 装配在那种形态下都能跑。

> 这个模拟是**必要的**：开发机上跑通不等于容器里跑通。它当场抓出一个容器会炸的问题——
> `anyio` 需要 `typing_extensions.sentinel`，而旧版本没有这个符号，
> 启动直接 `ImportError`。所以 `requirements.txt` 里显式钉了 `typing-extensions>=4.12`。

`live_chain.py` **只把密钥放在请求头里**传给服务器，服务器的代码路径里没有任何密钥回退——
它同时也就验证了 BYOK 链路本身。

## 八、公网部署

### 部署前必须做的一个决定：模型凭据

公开站**没有登录**，所以先想清楚模型调用由谁付钱：

* **本站出 Key**（访客零门槛）→ 在平台的环境变量里设 `SUITE_SERVER_LLM_KEY`。
  **代价：任何人拿到网址都能花你的钱，默认无上限。**
  被刷时设 `SUITE_RATE_LIMIT=60` 即可止血，不必改代码。
* **访客自带 Key**（不花钱）→ 什么都不配。但访客得先去申请一个 API Key，
  大多数人到这一步就走了。

详见第三节。**两种都不需要改代码，只差一个环境变量。**

### ⚠️ Hugging Face 已经不能免费跑 Docker Space 了

**2026 年 7 月起**，Hugging Face 把 Docker / Gradio Space 的免费额度收到了付费订阅后面。
免费账号调用建 Space 接口会得到：

```
HTTP 402  Static Spaces are free for everyone, but hosting Gradio and Docker Spaces
          on free cpu-basic requires a PRO subscription.
```

这是平台政策变化，不是本项目的问题。所以下面按"用哪个平台"分别说。

`Dockerfile` 已经做了兼容：**监听端口跟随平台的 `$PORT`**，
Hugging Face（固定 7860）与 Render / Railway（注入 `$PORT`）都能直接用。

### 方案一：支持 Docker 的免费托管（推荐，不需要信用卡）

据 2026-09 的公开对比（[free-cloud-deployment-platforms-2026](https://snapdeploy.dev/blog/free-cloud-deployment-platforms-2026-comparison)）：

| 平台 | 免费额度 | 信用卡 | 休眠 |
|---|---|---|---|
| **Render** | 750 小时/月，512 MB / 0.1 CPU，5 GB 流量 | 不需要 | 15 分钟无流量后休眠，约 1 分钟唤醒 |
| **SnapDeploy** | 4 个容器，100 小时/月 | 不需要 | 15 分钟无流量后休眠 |
| Railway | 30 天试用 $5，之后每月 $1 额度 | 不需要 | 默认不休眠 |
| Koyeb / Fly.io / Heroku | 免费额度已取消或需绑卡 | 需要 | — |

步骤（以 Render 为例）：

1. 登录 <https://dashboard.render.com>，选 **New → Web Service**
2. 连上 GitHub 仓库 `1844fp/123`（私有仓库也能连，Render 用 GitHub App 授权）
3. **Runtime** 选 `Docker`（Render 会自动读 `Dockerfile`）
4. 端口不用填——`Dockerfile` 读平台注入的 `$PORT`
5. 环境变量一个都不用配：站点是 BYOK 的，不含任何模型密钥
6. 创建后会分配公开地址，形如 `https://thesis-suite-xxxx.onrender.com`

可选环境变量见下表。

### 方案二：Hugging Face（需要 PRO 订阅）

如果你有或愿意订阅 HF PRO，`tools/push_hf.py` 可以直接一条命令部署：

```powershell
# 先做本地自检（不联网、不需要 token）
python tools\push_hf.py --offline-check

# 真部署
python tools\push_hf.py --token hf_你的write_token --space thesis-suite
```

脚本会自动探测代理（实测环境里 huggingface.co 直连超时，走 `127.0.0.1:7897` 才通）、
建 Space、分批上传 107 个文件、打印公开地址。

> 不要用**静态** Space 绕过收费：静态 Space 只跑前端，会丢掉 53 个本地检查器、
> Crossref 文献核验与服务端 BYOK 转发——站点最值钱的部分就没了。

### 可选环境变量

| 变量 | 用途 |
|---|---|
| `SUITE_CROSSREF_MAILTO` | Crossref 礼貌池邮箱，填了更不易被限流（非密钥） |
| `SUITE_ALLOW_CUSTOM_BASE_URL` | 设为 `1` 允许访客自带任意接口地址；不设则只放行内置服务商（防 SSRF） |
| `DSH_THESIS_DATA_DIR` | 数据目录，默认 `/app/data`（容器内是临时的） |
| `PORT` | 平台注入，`Dockerfile` 读它；本地 `docker run` 缺省 7860 |
| `SUITE_PQA_LIBS` | PaperQA2 的安装目录。默认引用 `E:\AI\thesis-assistant\libs-pqa`（1.19 GB，不复制）。**没有它，PaperQA2 那一块会明确报告不可用，其余功能照常** |
| `SUITE_ST_HOME` | 句子向量模型缓存目录，默认 `E:\AI\thesis-assistant\.tmp\st_home`（bge-small-zh-v1.5，91.9 MB）。本机访问不了 huggingface.co，所以复用现成缓存 |
| `SUITE_PQA_MAX_DOCS` | 单次索引的文献数上限，默认 40。每篇都要调一次模型 |
| `SUITE_PQA_MAX_DOC_CHARS` | 送进语料的单篇字符上限，默认 40000。超出会截断并在返回里如实标注 |
| `SUITE_PQA_LOCAL_KEY_FILE` | **显式**允许 PaperQA2 用某个本地凭据文件（本机自用图省事）。不设就完全不借任何密钥 |
| `SUITE_TIER_DIRECTORY` | 用外部 JSON 覆盖内置的核心期刊目录映射表。**整表替换，不合并** |

> `SUITE_PQA_LIBS` 与 `SUITE_ST_HOME` 的默认值指向本机的绝对路径，这是**有意的**：
> 公网容器里这两个路径不存在，PaperQA2 会自动报告不可用，其余五个助手完全不受影响。
> 也就是说这一块是"本机增强"，不是"部署前提"。

**已知限制**：会话数据只存在内存里。免费档平台会休眠，**休眠后会话清空**，
前端会提示重来。这是有意的取舍——本站定位是"一次性把一份稿子走完整条链路"，
不是长期论文管理平台。要长期保存请自己下载产物。

## 九、安全须知

* **不要把任何 API Key 提交进仓库。** `.gitignore` 已排除 `.env` / `models.json`

## 十一、能力边界（如实说明）

* **题目生成**：离线模式的质量取决于内置学科知识库的覆盖，冷门学科会明显偏弱。
* **资料获取**：抽取质量取决于访客贴进来的原文质量；逐字校验只能保证
  "引用的片段确实在原文里"，**不能保证原文本身可信**。
* **写作**：产出的是**初稿**，不是成稿。系统刻意不替作者做需要专业判断的结论；
  参考文献表只列真正被引用的条目，缺字段就留空，不补不编。
* **从文档导入**：读出的是**计划**（题名/结构/要求），不是"理解了你的研究"。
  长文档超出依据预算时只取前面一部分（界面会显示"用了几条 / 总共几条"）；
  扫描版 PDF 取不出文字，会明确提示需要 OCR 而不是假装导入成功。
* **评估**：53 个检查器查的是**形式问题**（引用编号、格式、数字是否有来源、
  写作结构），**不能判断"这个创新点够不够新"**这类需要同行评议的问题。
  评分由问题数量与严重度机械推导，不让模型打印象分——因为
  **模型给自己刚生成的稿子打分会系统性偏高**。
