# 三阶段写作说明（开题报告 → 初稿 → 终稿）

> 一句话：**写作被拆成三个交付单元，每个单元有自己的门槛、产出与通过标准；
> 门槛不满足时系统不会替你花掉那几十次模型调用。**

对应命令：`python -m app.cli phases`；阶段定义在 `app/phases.py`。

---

## 一、为什么分成三段，而不是"一键生成初稿"

原来的入口只有一个"一键生成"，它默认假设**你已经想清楚了**：有题目、有开题、
知识库里有资料。现实里这三件事的顺序是反的——大多数人是**先有模糊方向**，
要的是"帮我把开题写出来"，然后才谈初稿。

三个阶段的**失败模式完全不同**，这是拆开的真正理由：

| 阶段 | 最怕什么 | 所以门槛是 |
|---|---|---|
| 开题报告 | 选题本身立不住，后面几万字全白费 | 先过**选题体检**与**逻辑骨架自洽**，不过就不进写作 |
| 初稿 | 写得像但站不住（编造、无据、模板腔） | 每句话都要能溯源；写作检查器逐条过 |
| 终稿 | 看着完整但交上去被打回来 | 预审报告 + 未解致命问题数量决定能否放行 |

拆开还有一个副作用是好的：**"现在卡在哪一步"变成一个能回答的问题。**
一键生成只能回答"跑完了/没跑完"。

## 二、总览（数值全部取自 `app/phases.py`）

| | 开题报告 `proposal` | 初稿 `draft` | 终稿 `final` |
|---|---|---|---|
| **目标** | 把「想研究什么」写清楚，并且在动笔前证明这个选题立得住 | 按开题定下的框架，把每一章的正文写出来——写得像，而且站得住 | 把初稿打磨到能交出去：语言干净、前后一致、经得起审稿人读 |
| **交付物** | 开题报告 .docx（研究现状／研究内容／技术路线／创新点／进度安排／参考文献）+ 生成报告 | 论文初稿 .docx（各章正文 + 参考文献表）+ 生成报告（章字数、问题清单） | 论文终稿 .docx + 预审报告（五维、带严重度与投稿建议）＋（可选）返修指引 |
| **流水线阶段** | retrieve → draft → verify → fix → final | retrieve → draft → verify → fix → final | **verify → fix → final** |
| **绑定技能** | idea-evaluator、tech-paper-template、benchmark-paper-template、deep-research、vibe-research-workflow | paper-writer、intro-drafter、figure-designer、vibe-research-workflow | paper-polish、pre-submission-reviewer、rebuttal-guidance、figure-designer、vibe-research-workflow |

| **默认字数** | 8000 | 0 = 用论文类型建议字数（`app/writing/genres.py`） | 0 = 不改字数 |
| **检查清单** | 8 条 | 9 条 | 9 条 |
| **起跑门槛** | 3 条 | 2 条 | 1 条 |
| **通过标准** | 不允许存在未解决的致命问题；重要问题给出整改清单即可交付初稿评审 | 不允许存在未解决的致命问题（编造引用、数字无据、结论越界） | 未解决的 CRITICAL 必须为 0 才建议提交；有 CRITICAL 时预审结论只能是「先改再投」 |

## 三、三个阶段各自的细节

### 1. 开题报告（`proposal`）

**需要先有什么**：无。开题是链条的起点。

**产出结构（7 节，固定）**：

```
1. 选题依据与研究意义
2. 国内外研究现状及述评
3. 研究内容与研究目标
4. 拟采用的研究方法与技术路线
5. 研究重点、难点与创新之处
6. 研究进度安排
7. 主要参考文献
```

**检查清单**：论文类型明确（新方法／新问题／基准与评测）｜既有工作的局限最多三条且每条能指到具体文献｜关键思路能压缩成一句话｜关键挑战最多三条且与方法一一对应｜贡献三到四条、每条注明落在哪一节｜研究缺口不是"数据集太小"这类资源借口｜参考文献真实存在且作者读过｜没有任何编造的数字或结论。

**门槛（3 条）**：

1. 选题体检结论不是 `Reject and Pivot`（否则先把选题换掉，再谈写作）；
2. 逻辑骨架自洽检查全过（局限→思路→挑战→方法→贡献不断链）；
3. 知识库预检通过：题目与库里的资料相关，否则研究现状写不出来。

### 2. 初稿（`draft`）

**需要先有什么**：开题报告。**但真正阻断的是空的**——没有开题也能跑，
按论文类型的默认结构写（只是更泛）。这两件事在代码里是两个字段
（`requires` / `blocking_requires`），原因见第五节。

**产出结构**：`sections=()`，即**沿用开题解析出的章节树**；解析不出来才退回
论文类型默认结构（`_fallback_sections`）。

**检查清单**：每句事实性论断有来源角标且编号在文献表里找得到｜正文无占位标签与过程痕迹｜引言六段要素齐备｜综述按脉络组织而非逐篇罗列｜研究设计写到可复现粒度｜结果与讨论分开｜结论数字都能在正文找到且不引入新事实｜参考文献表只列真正被引用的｜图表有编号题注且正文先引用后出现。

**门槛（2 条）**：有开题报告或明确章节结构（没有框架的"一键初稿"会退化成泛泛而谈）｜知识库预检通过。

### 3. 终稿（`final`）

**需要先有什么**：初稿。**这一条真正阻断**——终稿是在已有稿子上打磨，
没有稿子就无从下手。

**产出结构**：不改章节结构。

**检查清单**：语言只改表达不改含义（数据／公式／引用／方法名一个没动）｜夸大词已清理｜没有超过 600 字的巨段也没有一句成段｜摘要具备目的／方法／结果／结论四要素｜破折号与 AI 腔用词密度回到正常范围｜摘要不是结论的换词版、同一发现在正文不超过三处｜图表题注给出结论｜参考文献编号连续、正文与文献表双向对应｜排版符合规范（用 `docx-format` 复核）。

**门槛（1 条）**：已有初稿正文。

**通过标准**：未解决的 `CRITICAL` 必须为 0 才建议提交。

## 四、`phase` 与 `stage` 的区别（最容易被混用的一处）

* **`stage` 是执行单元**（`app/framework/artifact.py` 的 `Stage`）：
  `gather / retrieve / draft / verify / fix / dedup / format / final`。
  顺序由 `app/pipeline.py` 的 `STAGE_ORDER` 固定，子集只筛**跑哪些**，不改顺序。
* **`phase` 是交付单元**（`app/phases.py` 的 `Phase`）：开题／初稿／终稿。
  一个 phase 跑若干 stage，并各自绑定章节结构、字数、技能与门槛。

混用这两个词的代价很具体：**"我只想重跑校对"会变成"我把整篇重写一遍"。**

### 终稿阶段不重新检索、不重新起草（实现点）

```python
# app/phases.py —— final
# 终稿不重新检索、不重新起草：只做校对、打磨与预审。
stages = (Stage.VERIFY.value, Stage.FIX.value, Stage.FINAL.value)
```

开题与初稿都是五段（`retrieve→draft→verify→fix→final`），**只有终稿是三段**。
这一行就是"终稿不会把你写好的东西重写一遍"的实现点：它不跑 `retrieve`
（不重新检索）、也不跑 `draft`（不重新起草）。

`app/finalize.py` 在此基础上只做四件事，且都**不动正文的事实内容**：

1. **语言打磨（可选）**：走 `writer:rewrite`，指令逐字对应 `paper-polish`
   （只改语言、不增删事实、不新增引用角标、拿不准就单独列出让作者确认），
   并自带保真校验（改写前后数字与角标必须一致），过不了就退回原文。
   跳过名单：摘要／关键词／结论／致谢／附录／参考文献——让模型"顺手"打磨这些最容易改出问题。
2. **校对与修复**：`stages = req.stages or phase.stages`，即 verify→fix→final。
3. **预审报告**：把问题按五个维度组织，给严重度计数与投稿建议，报告末尾附上终稿阶段的检查清单与通过标准。
4. **返修指引（可选）**：只有给了审稿意见原文才生成。

### 为什么"重跑一次"的语义必须靠 stage 表达

三个 phase 的 stage 组合放在一起看，差别只有一处，但那一处决定了功能能不能用：

| 场景 | 该跑的 stage | 不该跑的 stage | 用 phase 表达会怎样 |
|---|---|---|---|
| 初稿：这几章写得不好，重写 | draft → verify → fix | —— | `thesis --chapter …` 重跑初稿，正常 |
| 终稿：把语言清一遍 | final（+ 逐章 rewrite） | **retrieve、draft** | 如果用"重跑一键生成"表达，整篇会被重新检索、重新起草 |
| 只跑校对（不花模型钱） | verify | draft、fix | `run -p <项目id> -s verify` 即可 |
| 只重排版 | format（`docx-format`） | 其余全部 | 与写作阶段无关，独立命令 |

所以 `-s/--stages` 是**执行层**的旋钮，`--phase`／`final` 是**交付层**的旋钮。
一个 phase 之所以能"便宜地重跑"，是因为它的 stage 列表里没有贵的那两段。

### 终稿命令实际产出什么

跑一次 `final` 会写出四类文件，其中只有第 1 类是你的稿子：

1. `论文终稿.docx`——正文（打磨 + 修复后的版本）；
2. `终稿报告.md`——严重度计数、评分、打磨到了哪些章、**打磨未完成/被跳过的部分**、下一步、以及终稿阶段的检查清单；
3. `预审报告.md`——五维问题清单 + 严重度 + 投稿建议；
4. `返修指引.md`——只有传了 `--comments` 才生成。

**"如实说"这几处是刻意的**：打磨失败的章、被跳过的章、需要作者判断的问题条数，
都会写在报告里，避免"以为全篇都打磨过了"。

## 五、门槛为什么重要：这是一道"省钱闸门"

`app/phases.py` 的 `gate_report()` 顶部写着这句话：

> 一次初稿生成是几十次模型调用，一次终稿打磨也要几十次。

门槛不满足时不拦，作者会拿到一份**"看起来完整但引用着无关文献"**的稿子，
然后还得自己发现——那比直接说"先去补资料"糟糕得多。开题那两道门槛
（选题体检、骨架自洽）是最值钱的：**选题立不住时，写正文的几十次调用全部白花。**

三道闸门的实现方式不一样，这一点值得说清：

| 门槛 | 谁在判 | 判不了的部分怎么办 |
|---|---|---|
| 有初稿正文 | `gate_report(..., draft_text=...)` 直接查 | —— |
| 知识库预检通过 | `gate_report(..., precheck=...)` 读预检的 `usable` | —— |
| 选题体检不是 Reject and Pivot | `app/idea.py` 的 `review_idea`（模型按固定表格填 + 本地校验） | 语义部分只作为"给人看的问题"列出 |
| 逻辑骨架自洽 | `app/idea.py` 的 `check_skeleton`（四项自洽 `pass/fail`） | 同上 |

`gate_report` 的边界是刻意划的：**它只检查客观上能判的东西**——有没有前置阶段的产物、正文是否非空。
"选题好不好""逻辑自洽不自洽"交给 `idea` 工具，不在这里冒充能判。

**「需要」与「真正阻断」为什么要分开**（`Phase.blocking_requires` 的注释）：

* 初稿**需要**开题，但没有开题也能写（只是更泛）→ 不阻断，只提示；
* 终稿**需要**初稿，而没有初稿就完全没得打磨 → 阻断。

把"需要"全当阻断，会把"没有开题也想先写初稿"这种正常用法堵死。
另外一个刻意选择：**阶段绑定的技能没装只是 warning，不是 blocker**——
技能目录没了该降级成"少一段方法论提示词"，不该让写论文整个停摆。

门槛与"能检查的东西"之间还有一条自定的规矩：**允许用本地校验的地方，就不让模型自由发挥。**
选题体检与骨架自洽都是"让模型按固定表格填，再由本地代码核对字段名、条目上限、取值域"。
好处是检查便宜、可复现、能指出"哪一格填错了"；代价是**表格之外的语义判断一律不判**——
这条界线写在 `app/idea.py` 的模块注释里：能机检的机检，不能的明说不能。

## 六、怎么用

### 命令行

```powershell
# 列出三个阶段（各自的目标、产出、门槛、绑定技能；含未装技能的标记）
python -m app.cli phases
python -m app.cli phases --phase proposal        # 只看某一段的细节

# 开题报告
python -m app.cli proposal --topic "题目" -o 开题报告.docx

# 初稿（thesis 即 draft）
python -m app.cli thesis --topic "题目" -o 论文初稿.docx

# 终稿（要项目 id）
python -m app.cli final -p <项目id> -o 论文终稿.docx

# 选题体检（开题门槛之一）
python -m app.cli idea --topic "题目"

# 技能清单
python -m app.cli skills list
```

`--phase` 的当前取值只开放 `draft`（默认）与 `proposal`；终稿走独立的 `final` 命令
（`--phase` 的帮助文本里也这么写）。选题体检另有一个 `skeleton` 子动作，
用来单跑逻辑骨架自洽检查。

### 界面

三个阶段共用同一套流水线，界面上的差别只有三处：**选阶段 → 填题目/开题 →
拿产出**。终稿阶段必须先在项目列表里选一个已有初稿的项目——没有正文时
页面会直接给出 `gate_report` 的阻断原因，**不会开始产生模型费用**。

## 七、诚实边界：这些事工具不替你判断

三阶段把**流程**固化了，但下面这些判断始终在作者手上。工具报"通过"并不意味着它们成立：

| 不替你判断的事 | 为什么 |
|---|---|
| **结论是否成立** | 需要领域判断。选题体检只保证「该问的问题都问了、该有的证据缺口都标出来了」 |
| **创新点够不够** | 新意要与"最近工作"比对，需要联网检索与作者判断，`idea-evaluator` 的这条写在 `not_builtin` 里 |
| **实例是否真实** | 运行实例／案例的真实性只能由作者确认（引言六段式的 `not_builtin`） |
| **图好不好看** | 字号、位图痕迹、配色是否色盲友好要看图；本项目只处理文字稿（`figure-designer` 的 `not_builtin`） |
| **查重与 AIGC 检测** | 需要外部工具。终稿报告的"下一步"里明确写着"最后自行完成查重与 AIGC 检测——本系统不做这两件事" |

另外两条**工具明确说过做不到**的：

* **"这句话是用户给的还是模型记的"无法自动判定**（`paper-writer` 的 `not_builtin`）；
* **"这次编辑有没有改变科学含义"最终要作者确认**（`paper-polish` 的 `not_builtin`）。
  保真校验只能证明**数字与角标一字不差**，证明不了语义没被挪动。

预审报告里那部分"待作者判断"的问题会被单独计数报出，文案固定为：
"这些是工具不替你决定的问题：结论是否成立、创新点是否够、论证是否充分。"

### 还有三件事，三阶段本身不保证

1. **阶段顺序不等于质量顺序。** 骨架自洽只保证"局限→思路→挑战→方法→贡献"不断链，
   **不断链 ≠ 链子是对的**：三条局限可以都是真的、又都不是你要解决的那个。
2. **通过标准只统计"未解决的致命问题数"。** 严重度是工具按"是否阻止投稿"定的，
   它不评价选题的价值——一份 0 个 CRITICAL 的稿子仍然可能毫无新意。
3. **开题报告的字数（8000）是常见要求，不是硬指标。** 各校模板不同，
   用 `--words` 覆盖，或用 `--section` 换成学校要求的小节。

## 八、常见卡点与排查

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `final` 直接退出、没花钱 | 项目里没有正文，门槛拦下了 | 先跑初稿，或把已有稿子导入为初稿；阻断原因原文会打印出来 |
| `idea` 返回非零退出码 | 选题体检校验不过，或结论是 `Reject and Pivot` | 这是刻意设计（便于脚本化"先体检再写作"）；看报告里"先修这些问题"那一节 |
| 终稿报告的"打磨到的章节"比预期少 | 摘要／关键词／结论／致谢／附录／参考文献在跳过名单里，或该章正文不足 400 字 | 跳过原因会列在报告的"打磨未完成的部分" |
| `phases` 报某技能"未安装" | 该技能本机没有，对应方法论指令不会进提示词 | 是 warning 不是阻断；装法见 `Skills集成说明.md` |
| 阶段跑完报告写"通过"，但稿子仍不能交 | 门槛与检查器只覆盖可机检的部分 | 见第七节；查重、AIGC、结论成立性始终要自己做 |

| `app/phases.py` | 三阶段定义（目标／交付物／依赖／stage／技能／结构／字数／清单／门槛／通过标准）与 `gate_report` |
| `app/thesis.py` | `ThesisRequest.phase` 与 `build_brief`：phase 决定章节结构（阶段默认结构 > 论文类型默认结构）与目标字数 |
| `app/finalize.py` | 终稿编排：打磨（可选）→ verify→fix→final → 预审报告 → 返修指引（可选）→ 导出 |
| `app/idea.py` | 选题体检与骨架自洽：严格 JSON 契约 + 本地校验 |
| `app/rebuttal.py` | 返修指引：纯本地、零模型成本、结果可复现 |
| `app/skills_registry.yaml` | 每个技能绑定到哪些阶段（`phases` 字段） |
