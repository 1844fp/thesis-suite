# 借鉴 Supervisor-Skills：把科研方法论落成可检查的规则

> 来源：**Supervisor-Skills**，香港科技大学（广州）DIAL 实验室开源
> <https://github.com/HKUSTDial/Supervisor-Skills>
> 作者：骆昱宇（Yuyu Luo）等。
> 许可：`skills/intro-drafter`、`skills/paper-writer` 为 **CC BY-NC-SA 4.0**；
> `skills/tech-paper-template`、`skills/pre-submission-reviewer` 为 **CC BY 4.0**。
> 本项目**不复制**其提示词文本，只把其中可判定的规则重新实现为检查器与蓝图，
> 并按许可要求注明来源。本项目为个人非商业用途。

---

## 一、取什么、不取什么

那个项目是**给 AI 助手的技能包**（SKILL.md + 提示词），面向顶会论文；
本系统是**带 50 个检查器的写作流水线**，面向中文学位论文。
两者定位不同，所以不能照搬。取舍的判据只有一条，也是本项目的核心纪律：

> **提示词里提的每一条要求，都必须能被检查出来。只提要求不检查，等于给模型一个愿望。**

按这条判据，他们的技能分成三类：

| 类别 | 例子 | 本项目的处理 |
|---|---|---|
| **可机械判定** | 贡献条目里有没有空话；正文数字能不能溯源；宣传腔密度 | ✅ 落成检查器 |
| **可按类型分流的构造规范** | 技术类引言的六段式 vs 人文社科的 CARS 三语步 | ✅ 落成蓝图，按论文类型分流 |
| **纯提示词约束** | "不要编造"、"措辞强度不超过证据强度"、"内部规划不要泄漏" | ⚠ 只强化提示词，**不假装能检查** |

第三类必须诚实：**「不要编造」这句话本身没法机械检查**。本项目已有的做法是
"角标越界就删并计数"——那是可验证的部分；剩下"这句话是不是编的"仍然需要作者。
所以这里不会因为它被写进了提示词就宣称它被保证了。

## 二、落成了什么

### 1. 技术类引言六段式（按研究方法分流）

他们在 `intro-drafter` 里给了一套六段式流程，并**自己写明了适用范围**：

> 六段式是为 STEM 与技术类论文设计的。若研究方法属于人文、社科、经济、法学，
> 不要用这套骨架硬套。

这条边界与本项目的论文类型系统正好对上——所以实现成：

* **技术类**（`engineering` 设计开发型、`experimental` 实验研究型）走六段式：
  背景与运行实例 → 已有工作的局限 → 问题本质与目标 → 关键挑战 → 方案概览 → 贡献；
* **其余类型**继续走 CARS 三语步（Swales 1990）。

分流判据在 `app/writing/__init__.py` 的 `TECH_INTRO_GENRES`，
对应他们那句"**按研究方法判断，不按学科名判断**"——
一个用问卷做实证的教育学论文不是技术类，一个做算法改进的社科论文反而是。

两个蓝图的 `kind` 都是 `introduction`，所以**检查器不会因为选了哪个蓝图而漏跑**。

### 2. 四条可判定的自洽性检查 → 三个检查器

他们给了四条自洽性检查（局限→关键思路→挑战→模块→贡献），每条失败都是 CRITICAL。
其中**语义部分无法机械判定**（"这条挑战是否真的回应了那条局限"要读全文），
所以只落可判定的部分：

| 检查器 | 判定口径 | 严重度 |
|---|---|---|
| `check_limitation_challenge_chain` | 列了挑战却没交代已有工作的局限 → 报出 | major |
| `check_contributions_specific` | 贡献条目命中空话词表（"进行了大量的实验""取得了良好的效果"）或过短 → 逐条报出 | major |
| `check_contributions_map_sections` | 贡献条目都没绑定章节落点 → 报出 | major |

只判**形式上缺环**，不判语义对不对——不做假承诺比多报一条更重要。

### 3. 不编造量级 → `check_number_grounding`（本次最有价值的一条）

他们在 `paper-writer` 里给的硬规则是"不编造场景、机制、量级、流程、标识符"，
并且"措辞强度不得超过证据强度"。其中**量级是唯一能机械验证的一类**：

> 数字的字面比对不需要理解语义，就能证伪"这个数从没在证据里出现过"。

所以实现了：**正文里的数字必须能在本章检索到的证据里找到**。
本系统本来就有证据台账（哪一章检索到了哪些原文），所以这条能直接落地。

判据**刻意保守**，只查两位数以上或带小数点的数：

* 1~9 的小数字绝大多数是枚举（"3 个方面"）或序数，是误报的主要来源，一律不查；
* 年份、百分比、样本量、系数通常两位以上，正好落在范围内。

这么做是因为**误报会毁掉工具可信度**：一条"这个 3 没有依据"的假警报，
会让作者连同真问题一起忽略。

注意这条只覆盖"数字"这一类。**场景、机制、流程、标识符的编造仍然查不了**——
那需要知道作者给过什么。所以他们那条规则在本项目里是**部分落实**，不是全部。

### 4. 宣传腔词表 → `check_ai_tone_vocabulary`

他们的 banned AI-tone vocabulary 列表（英文）在这里扩成中英双语：
革命性 / 开创性 / 前所未有 / 突破性 / 颠覆性 / 里程碑 / 卓越 / 赋能 / 助力 /
深度融合 / innovative / pioneering / revolutionary / unprecedented / breakthrough …

与本项目已有检查器的**分工**：

| 检查器 | 管什么 |
|---|---|
| `check_template_connectives` | 空转连接词（"综上所述""值得注意的是"） |
| `check_overclaim` | 以"本文"为主语的夸大断言（"首次提出""填补空白"） |
| **`check_ai_tone_vocabulary`** | **宣传性形容词与动词**——它们不构成断言，所以前两个抓不到 |

用**密度**判定而不是出现次数：学术写作里偶尔出现"创新"是正常的。

### 5. 审稿意见书 → `app/review.py`

`pre-submission-reviewer` 的输出格式与三条诚信规则是这次收获里最实用的一块。
本项目已有的 50 个检查器产出的是一份**平铺的清单**——它能说明"有哪些问题"，
但说明不了"这些问题合起来意味着什么、现在能不能交"。

所以新增 `review` 命令 / 「问题」页签的「生成审稿意见书」按钮：
把问题按五个维度（宏观逻辑 / 写作细节 / 语言与格式 / 引用与文献 / 图表与公式）组织，
给出评分与提交建议。

**三条诚信规则由代码强制，不由模型自觉：**

1. **每条发现必须引用具体原文。** 没有 `evidence` 的问题不进正文，
   被剔除的条数如实报出（实测一份稿子里有 7 条这样的）；
2. **致命问题缺修改建议时逐条提示**；
3. **评分与提交建议由问题数量机械推导**——致命问题存在时分数硬性封顶 6.0，
   且结论必定是"须修改后再提交"。

第三条最要紧：**模型给自己刚生成的稿子打分会系统性偏高**，
而"能不能交"这个判断一旦失真，整份意见书就没有意义了。所以它是算式，不是印象分。

另外按同一类问题归并（10 处「一篇论文半句话」的建议本来就一样，逐条重复十遍
会把表格撑成一堵墙），但**逐处的原文引用仍然保留**——那是作者定位问题的唯一依据。

## 三、实现过程中抓到的三个真实缺陷

### 1. 贡献条目根本没被读到

`check_contributions_specific` 第一版只取"含贡献标记的那一段"。而贡献通常写成：

```
本文的主要贡献如下：
1. 提出……
2. 提出……
```

标记在**上一行**，条目在**后面的行**里。于是检查器拿到一句
「本文的主要贡献如下：」然后判定"没有条目"——**它永远不会报**，
而"永远不报"看起来像"贡献写得很规范"。

这类"检查器静默失效"是本项目记过多次的失败模式（`app/checks/__init__.py` 顶部
专门写了这条纪律）。修法是从标记位置**往后扫**，收集连续编号条目，
遇到空行或标题收尾；没有编号时按"第一，/其二，"这类序列词回退切分。

### 2. 同一个坑踩第二次：长度门槛把最该报的样本挡在外面

`check_ai_tone_vocabulary` 初版把长度门槛定在 400 字，结果一段堆满宣传腔的
240 字样本**因为不达门槛被整段跳过**。

这与 `check_template_connectives` 当初的故障一模一样——那次是 177 字的纯套话样本
被 200 字的门槛挡掉，注释里还留着记录。密度是千分比，本来就与文本长度无关；
长度门槛只用来挡"短到没有统计意义"的片段。已统一降到 120 字。

**这个坑重复出现说明一件事**：新写检查器时，"长度门槛"是最容易顺手定高的一项，
而它的失效方式是静默的——样本越短越报不出来，恰好与"最该报的极端样本"重合。

### 3. 数字溯源检查在真实论文上误报 17 处——三种"同义写法"

`check_number_grounding` 第一版做**字面比对**。在一篇 2.7 万字的真实论文上跑，
报出 17 个"证据里没有的数字"。逐个核对后发现**绝大多数是误报**：

| 证据里的写法 | 正文里的写法 | 根因 |
|---|---|---|
| `8 800个观测值`、`23 008 个样本观测值` | `8800`、`23008` | 千分位被留成空格 |
| `均值为0. 072，标准差为0. 268` | `0.072`、`0.268` | 小数点后被留成空格 |
| `标准差为1．166`（U+FF0E 全角句点） | `1.166` | **全角小数点** |

三种都来自 PDF 抽取 + 中文排版。第三种最隐蔽——三个字符肉眼几乎一样，
只有把两串字符放在一起比对才看得出。一条真实论文里前两种和第三种同时出现。

修法是在 `fact_numbers` 里统一归一化（那个函数是"什么算事实数字"的**唯一实现**，
`check_conclusion_grounding` 与结论生成端共用它，所以一处修、三处受益）。

**修完之后，17 处降到 4 处，而剩下的 4 个都是真问题**：

```
出现本章证据中没有的数字：0.287、10.309、40.6、45
```

证据里只写了「最小值与最大值分别为18．251、28．560」，
而正文里的「极差达 10.309，约为均值的 45%」是**模型自己算出来的**
（28.560−18.251=10.309，10.309/22.910≈45%）。

这正对应 Supervisor-Skills 那条规则："不编造量级"、"措辞强度不得超过证据强度"——
一个由模型推导出来的数，**放在引用统计量的同一句里，读者会以为它来自原文**。
作者需要自己判断这个推导是否该保留。

**这一条值得记下来的原因**：假件测试永远发现不了它。只有当检查器在真实数据上跑过，
才会发现"同一个数在被引文献里有三种写法"。这类**格式层的现实**必须靠真实语料验证。

### 4. 顺带发现：项目文件带 BOM 就打不开

修上面那个误报时，我用 PowerShell 改了项目的 `project.json`，
`Set-Content -Encoding UTF8` 自动加了 BOM，于是**整个项目打不开了**，
报的是 `Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1`。

BOM 不产生任何可见字符，却是 Windows 上极常见的产物（记事本、PowerShell、
不少编辑器都会加）。而"项目文件打不开"对作者来说是很重的故障——
他看不到稿子、问题清单、版本链。为了一个不可见的前缀把整份项目拒之门外，
代价与收益完全不成比例。已改为用 `utf-8-sig` 读：有 BOM 就吃掉，没有也照常。

## 四、验证

```powershell
# Supervisor-Skills 方法论的落地测试（53 项）
.\run_python.cmd tools\test_supervisor.py
```

每组都是**好坏成对**的断言：好文本必须不被报，坏文本必须被报。
只测"坏文本被报出"是不够的——那样一个"永远报出"的检查器也能通过。

覆盖：技术类引言分流、四个新检查器、数字溯源、审稿意见书的三条诚信规则。

实际用法：

```powershell
# 生成模拟审稿意见书
.\run_python.cmd -m app.cli review -p <项目id> --open-only -o 审稿意见书.md
```

界面在「问题」页签右上角的「生成审稿意见书」。

## 五、没有取的部分，以及为什么

| 技能 | 为什么没接 |
|---|---|
| `idea-evaluator`（五维 Idea 评估） | 评估"选题够不够新"需要领域判断。本系统可以把它做成提示词，但那只是给模型一个愿望——本项目不假装能检查它。**但选题评估确实是个真需求**，值得将来单独做（可以做成"给作者的自查清单"而不是"自动评分"）。 |
| `deep-research`（综述级调研） | 本项目的 RAG 检索 + 相关性闸门已覆盖"取材"这一半；MECE 分类综合需要跨文献的语义归类，机械判定不了。 |
| `paper-polish`（中译英润色） | 本系统面向中文学位论文，`writer:polish` 已覆盖中文润色 + 保真校验。中译英是另一个场景。 |
| `figure-designer` / `drawio-reconstruction` | 需要图像生成与 drawio 工具链，与当前流水线不在一个层面。**科研作图是学位论文的真实缺口**，值得将来单独立项。 |
| `benchmark-paper-template` | 面向 benchmark 类顶会论文，学位论文里没有这个体裁。 |
| `rebuttal-guidance` | 面向会议 rebuttal。学位论文对应的是**答辩准备**，是个可做的方向（用现有问题清单生成"可能被追问的点"），但那是另一个功能。 |
| `vibe-research-workflow` | 讲 AI 辅助科研的工具选型与行为规则，是给作者读的方法论，不是可执行检查。 |
