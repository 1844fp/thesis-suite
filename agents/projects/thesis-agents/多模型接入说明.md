# 多模型接入：换厂商、按用途分配、成本可见

> 这份文档说清楚**怎么接不同的模型 API**，以及为什么"按用途分配"值得配。
> 界面在 **模型** 页签；命令行是 `models` 命令。

---

## 一、为什么需要按用途分配模型

一次论文生成要发起 **40~60 次模型调用**，而这些调用的性质完全不同：

| 用途 | 性质 | 值得用多好的模型 |
|---|---|---|
| `draft` 起草正文 | 决定成稿质量，最长（每单元 1200~2500 字） | **最强** |
| `plan` 规划大纲 | 一次调用，决定整篇结构 | 好 |
| `conclude` 结论汇总 | 一次调用，依据已在正文里 | 够用即可 |
| `rewrite` 按你的要求改写 | 次数少，但改的是你指定要改的地方 | 好 |
| `verify` 模型检查器 | 判断句、核验，调用次数多 | **便宜** |
| `fix` 自动修复 | 机械改写，调用次数最多（实测 23 次） | **便宜** |
| `polish` 润色 | 只改表达 | 便宜 |

原先全局只有一个模型，作者面对一个两难：**用好模型，一次生成几十次调用花掉不少钱；
用便宜模型，正文质量跟着掉**。分开配就绕开了这个两难——起草用强模型、
核验与修复用便宜模型。

配置上没有"必须全配"的要求：**留空的用途自动落到当前激活的档案**。
只配一个也能用，按用途分配是可选的精调。

## 二、界面（推荐）

**模型** 页签 → 选一个厂商预设 → 点「套用预设」→ 填密钥 → 「先测一下」→ 「保存并设为当前」。

- **测试**按钮会**真实调用一次**（几秒钟、成本可忽略）。字段填全但密钥错、模型名不存在、
  余额不足、地址少个 `/v1`——这四种只有真调一次才发现得了，而它们的表现都是
  "生成到一半才失败"，那时代价已经付出了。
- **「逐个测试全部」**一次测完所有档案，配了多个厂商时不用一个个点。
  没有填全的档案会被跳过并说明缺什么，不会发一个注定失败的请求。
- **按用途分配**卡片里给每个用途选一个档案，留空表示用当前档案。
- 右侧「当前实际路由」实时显示每个用途最终会走哪个模型。

写作页签顶部还有一个「本次模型」下拉：**只影响这一次生成**，不改你的长期配置。

## 三、命令行

```powershell
# 看有哪些厂商可选
.\run_python.cmd -m app.cli models presets

# 加一个档案（预设 + 密钥）。密钥不填时会尝试沿用 .env 里同地址的那把
.\run_python.cmd -m app.cli models add --id deepseek --preset deepseek --key sk-xxx --use

# 加一个便宜档，专门用来做核验与修复
.\run_python.cmd -m app.cli models add --id cheap --preset zhipu --model glm-4-flash --key yyy

# 按用途分配：起草用好模型，核验与修复走便宜档
.\run_python.cmd -m app.cli models role --set verify=cheap --set fix=cheap

# 看全部档案与用途分配
.\run_python.cmd -m app.cli models list

# 测连通性（会真发一次请求）
.\run_python.cmd -m app.cli models test --id cheap

# 配了多个厂商时，逐个测一遍
.\run_python.cmd -m app.cli models test --all

# 切换当前档案 / 删除 / 清空某用途
.\run_python.cmd -m app.cli models use deepseek
.\run_python.cmd -m app.cli models remove cheap
.\run_python.cmd -m app.cli models role --set verify=

# 只让这一次生成用指定档案
.\run_python.cmd -m app.cli thesis --topic "题目" --model cheap
.\run_python.cmd -m app.cli rewrite -p <项目id> --section 第3章 --instruction "…" --model cheap
```

## 四、支持的厂商

都走 **OpenAI 兼容协议**，差别只在 `base_url` 与模型名：

| 预设 | API 地址 | 建议模型 |
|---|---|---|
| `deepseek` | `https://api.deepseek.com/v1` | `deepseek-chat`（`deepseek-reasoner` 更会分析但慢） |
| `zhipu` 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus`（`glm-4-flash` 很便宜） |
| `dashscope` 通义 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus`（`qwen-turbo` 便宜、`qwen-max` 强） |
| `moonshot` Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-32k` |
| `ark` 火山方舟 | `https://ark.cn-beijing.volces.com/api/v3` | 填你的**接入点 ID**（`ep-…`），不是模型代号 |
| `baichuan` 百川 | `https://api.baichuan-ai.com/v1` | `Baichuan4` |
| `minimax` | `https://api.minimax.chat/v1` | `abab6.5s-chat` |
| `openai` | `https://api.openai.com/v1` | `gpt-4o-mini` |
| `ollama` 本地 | `http://127.0.0.1:11434/v1` | `qwen2.5:14b`，不要 key |
| `vllm` 自建 | `http://127.0.0.1:8000/v1` | 自填 |
| `custom` | 自填 | 自填 |

**模型名是建议值，不是承诺。** 各家的模型会上下线、改名，工具没法跟着变。
界面上这个字段始终可改；填错了「测试」按钮会立刻告诉你。**以厂商文档为准。**

### 本地模型

Ollama / vLLM / LM Studio / llama.cpp server 都能接。密钥随便填一个占位值
（如 `ollama`）——很多本地服务不校验它，但客户端要求非空。

本地模型的实用定位是**核验与自动修复**（判断句、机械改写），
起草正文的质量取决于模型本身。

## 五、配置存在哪儿

* **`models.json`**（项目根目录，与 `.env` 同级）——档案、当前激活项、用途分配。
  **含明文密钥**，与 `.env` 同一信任级别。
* **`.env`** 里的 `LLM_*` 仍然有效，并且：

  * **没有 models.json 时**，`LLM_*` 就是全部配置——老配置一个字都不用改；
  * **有档案时**，档案里**没填的字段**沿用 `LLM_*` 的值。所以"只改 base_url、
    密钥沿用原来的"这种常见情形不用重复填密钥。

### 密钥什么时候会被复制

加档案时如果没给 `--key`，命令会尝试沿用已有配置里的密钥，但**只在
`base_url` 完全相同的时候**。原因很直接：不同地址几乎一定是不同厂商，
把 A 家的密钥发到 B 家的服务器上是实打实的凭据泄露。
地址不同就留空并提示你填。

### 密钥会不会漏出去

* 给界面/API 的视图（`GET /api/models`）**只出脱敏串**（`sk-ab••••••••6789`），
  任何情况下不含明文。界面的 JSON 会被浏览器缓存、被日志记录、被截图，
  这条不能出错。
* 明文只在 `models.json` 里（`as_dict(mask=False)`，仅供落盘）。
* 落盘与展示用的是**两个不同的序列化函数**——这一点踩过：原先 `save()` 复用了
  给界面看的那个，字段名对不上，**密钥写进文件又读不回来**：界面显示"已填全"、
  重启后变成"未填全"，而文件里那个键名看着还挺像回事。现在 `tools/test_models.py`
  逐个字段做往返断言钉住它。

## 六、成本台账会告诉你每个模型用了多少次

报告与命令行里现在会按模型汇总：

```
模型调用：39 次，失败 0，耗时 163.7s
    · deepseek-chat：31 次，128.9s
    · glm-4-flash：8 次，34.8s
```

生成报告里还有一张表，写明**本次每个用途实际用的哪个模型**：

| 模型 | 调用次数 | 耗时(s) | 失败 |
|---|---:|---:|---:|
| `deepseek-chat` | 31 | 128.9 | 0 |
| `glm-4-flash` | 8 | 34.8 | 0 |

顺带修了一个一直存在的小毛病：台账的 `model` 字段原先取自
`kwargs.get("model")`，而 `chat()` 的签名里根本没有这个参数——**它永远是空串**。
后果是台账只能说"调了 47 次"，说不出"是哪几个模型、各调了多少次"。
按用途分模型之后，这正好是作者最需要看的那一项，所以一并修了。

## 七、测试

```powershell
# 多模型接入（54 项）：预设、档案往返、密钥不外泄、按用途路由、失败可读
.\run_python.cmd tools\test_models.py

# 其余回归
.\run_python.cmd tools\test_generic.py
.\run_python.cmd tools\test_thesis.py
.\run_python.cmd tools\test_writer.py
```

`test_models.py` 里几条值得单独说：

* **逐个字段做往返断言**——档案存盘再读回来必须一模一样，尤其是密钥；
* **公开视图里不能出现明文密钥**（直接对 JSON 串做子串断言）；
* **用途指向不存在的档案时退回激活档案而不是崩**，并且把这件事记下来；
* **测试连通性的失败必须可读**，且结果里带上实际用的模型名与地址便于核对。

## 八、这套机制不做的事

1. **不校验模型名是否真实存在。** 各家命名规则不同，工具只负责把你的请求发出去、
   把错误原样返回。填错了「测试」会立刻告诉你。
2. **不比较模型效果。** "哪个模型写论文更好"是需要你自己试的判断，不是配置项。
3. **不自动降级。** 某个用途配的模型失败了，不会偷偷换一个模型重试——
   那会让"这一章是谁写的"变得说不清。失败就失败，如实报告。
4. **不做额度管理。** 余额不足时报的是服务商返回的原文。
