> 这份文档说明**这条链路做了什么、依据什么、以及它明确不做哪些事**。

## 一、怎么用

### 命令行

```powershell
cd E:\AI\thesis-agents

# 1. 先看系统把你的开题读成了什么（纯规则解析，不调用模型，不花钱）
.\run_python.cmd -m app.cli propose 开题报告.docx

# 2. 一键生成（论文初稿 .docx + 生成报告 .md）
.\run_python.cmd -m app.cli thesis --proposal 开题报告.docx --author 你的姓名 --words 35000
```

`thesis` 会在结束后打印：

```
完成：612.4s  项目 prj-20261010-xxxxxx
  题目：数据资产的估值与计量——以科大讯飞为例
  正文：34 812 字（6 章）
  ✅ retrieve  检索到 N 条证据
  ✅ draft     writer:plan：大纲已生成…；writer:draft：已起草 5 章…；…
  ✅ verify    运行 45 个检查器，发现 132 条待处理问题
  ✅ fix       2 轮，收敛=True
  ✅ final     流程结束

问题统计：致命 1 · 重要 5 · 轻微 12 · 提示 9 · 待人工 98
模型调用：47 次，失败 0，耗时 186.9s

✅ 稿件：一键生成_硕士论文初稿.docx
    116 段 · 标题 21 个 · 文献 36 条 · 待办标记 57 处
📋 生成报告：一键生成_硕士论文初稿_生成报告.md
```

### 界面

启动 `.\run.cmd` 后打开 <http://127.0.0.1:8780>，「一键生成」是第一个标签页：
上传开题报告 → **点「解析预览」确认结构** → 点「开始一键生成」。
进度实时滚动，结束后可直接下载 .docx 与生成报告。

### 常用参数

| 参数 | 说明 |
|---|---|
| `--proposal X.docx` | 开题报告（.docx/.txt/.md）。不给则退回内置六章结构 |
| `--title` | 论文题目。不给则用开题里的题目 |
| `--words 35000` | 目标字数。**按章节职能分配**，不平均分（见第三节） |
| `--section "绪论" --section "文献综述"` | 手工指定章节，**覆盖**开题的章节树 |
| `--no-export` | 只生成正文，不导出 .docx |
| `--llm-verify` | 启用需要模型的检查器（更全面，也更花钱） |
| `--with-dedup` | 附加降 AIGC 阶段（需 aigc-reducer 在线） |
| `-s draft` | 只跑写作（规划→起草→结论→文献表） |

## 二、这条链路做了什么

```
开题报告.docx
  → ① 结构化解析      题目／章节树／研究方法／案例对象／创新点备忘／参考文献
  → ② 建项目          把开题变成"写作意图"，**不把开题当成稿件**
  → ③ 写作规划        按开题章节逐章检索证据 + 按章节职能分配字数
  → ④ 逐章起草        每章按小节切成多个写作单元，只依据检索到的证据说话
  → ⑤ 结论汇总        只依据已写正文，逐条标注依据章节
  → ⑥ 参考文献表      角标按出现顺序连续化 + 生成文献表
  → ⑦ 验证与自我更正  45 个检查器；可机械修的问题自动修，需判断的交还作者
  → ⑧ 导出            规范排版的 .docx（待办标记标红）+ 生成报告
```

### ① 开题报告解析：为什么用规则而不是模型

中文开题报告的栏目名高度固定（选题背景、国内外研究现状及述评、基本内容与结构框架、
拟采用的研究方法、重点难点、主要参考文献）。所以解析**用规则，不调用模型**：

* 结果可逐条回溯到原文行号，你能核对"系统理解的第三章是不是你的第三章"；
* 模型解析会给出一份"看起来对"的结构，错了也看不出来——而结构错了，
  后面几万字全部白费。

**最有价值的产出是「结构框架」里的章节树。** 实测的《开题报告四》解析出：

```
第五章 案例分析——以科大讯飞为例
  - 公司介绍
  - 数据资产的确认与计量属性选择
  - 评估参数确定
  - 数据资产计量方案模拟
  - 数据资产评估结果及验证
  - 模型适用性与局限性讨论
```

这 6 个小节直接成为这一章的 6 个写作单元。**作者的章节划分被优先遵守**：
模型现编的小节只在作者没列小节时使用。

抽不到的栏目**写入警告并留空**，不用默认值填。一份如实标出"没找到研究方法那一段"
的报告，比一份字段齐全但一半是猜的更有用。

### ③ 字数按章节职能分配，不平均分

平均分是错的：文献综述与核心分析章各占两成以上，结论只占一成左右。平均分会把结论
撑成一篇啰嗦的复述，同时把最需要篇幅的核心章饿死。

| 章节类型 | 建议占比 |
|---|---|
| 绪论 | 10% |
| 文献综述 | 22% |
| 研究设计 | 13% |
| 实证结果/核心分析 | 26% |
| 讨论 | 17% |
| 结论 | 9% |

单章设了上下限（900～12000 字），所以分配之和可能与目标有偏差——
偏差会如实写进大纲的 `word_plan_note`，不假装刚好等于目标。

### ④ 一章不是一个写作单元

一份硕士论文的核心章常在 6000～12000 字。单次生成写不了这么长：模型的输出上限
与"写得越长越注水"的倾向都会让结果退化。所以按小节把一章切成一串写作单元，
每个单元 1200～2500 字、单独挑最相关的证据、单独生成，最后拼回本章。

**拆分不会编造新的小节标题。** 小节太长时按蓝图的结构骨架拆成"同一小节的上/下部分"，
两部分共用同一个小节标题，只靠提示词里的"本部分侧重"区分。理由是：为了切分而编造
「1.1.1 ……」会让成稿出现作者从未同意过的目录项，而目录是评审对照开题检查的第一样东西。

## 三、四条不容妥协的界线

### 1. 创新点：任何环节都不生成

开题报告里的"拟创新之处"被原样提取出来，**只作备忘录**放进生成报告，供你写结论时对照。
它不会进入生成环节。

章节政策分三档（`app/agents/writer_common.py`）：

| 档位 | 适用章节 | 处理方式 |
|---|---|---|
| `never` | 创新点、致谢、声明、附录 | **任何环节都不生成** |
| `structure_draft` | 结论、结语、总结、展望 | 只依据正文汇总，整章标记待作者逐条确认 |
| `auto` | 绪论、综述、研究设计、结果、讨论 | 正常起草 |

匹配用**子串**而不是前缀：开题里的章节常写成「拟创新之处」「本文的创新点」「5.3 未来展望」，
前缀匹配会漏掉它们——而漏掉的后果是起草环节**真的去替作者写创新点**。

### 2. 结论：只汇总正文，不新造事实

结论的素材来自**你已写的正文**（逐字抽取各章的判断句作为论断清单），不是知识库检索结果。
所以它的正确性判据与其它章完全不同——其它章看"有没有依据"，结论看**"有没有超出正文"**。

三道机械闸门：

* 结论里出现的每个数字，都必须能在正文中找到；找不到的**保留原句、就地标注**
  `【待作者补充：本句的数字「X」未在正文中出现，请核对或删除】`。
  不删句子的原因：数字是句子内容的一部分，删掉会把句子改得不成话，你反而看不出原本想说什么。
* 角标的可选范围是**正文里已经引用过的编号**，不是整个证据池。结论里冒出一条正文没引过的
  文献，说明这条结论的支撑不在正文里。
* 出现「本文的创新之处」「首次提出」「填补了……空白」即报**致命**问题。

### 3. 引用编号全篇唯一

原先按章检索、每章从 `[1]` 开始编号。单章看没问题，但整篇合并后绪论的 `[1]` 与综述的
`[1]` 指向不同文献——**一份学位论文只有一张参考文献表，这是实打实的引用错误。**

修法不是"最后重排一下编号"（那只是把错误藏起来），而是从检索那一刻起就分配全篇唯一编号：

* `EvidencePool` 是项目级证据池，编号单调递增、只增不改；
* 同一段原文被两章分别检索到时**拿到同一个编号**（按 `doc_id + 页码 + 原文哈希` 去重）；
* 校验角标时只认"本次提示词里给过模型的编号"——编号是全局的，可见范围是局部的，
  所以模型既编不出池外的号，也编不出它没见过的号。

定稿前按角标**首次出现顺序**重排为连续编号，并据此生成文献表。这一步是纯文本变换，
产出映射表，可复验。

### 3.1 编号的单位是「文献」，不是「证据段落」

证据池里的每一条是一个**原文片段**（带页码），这是为了让每句论断都能追回具体出处。
但参考文献表列的是**文献**。两者混淆的后果实测出现过：

```
证据池： 1=陈荣达(第1页)  2=陈荣达(第3页)  3=陈荣达(第5页)  …
文献表： [1] 陈荣达…  [2] 陈荣达…  [3] 陈荣达…   ← 同一篇论文列了五遍
```

GB/T 7714 的顺序编码制要求**同一篇文献只有一个编号**（被引多次就复用同一个号）。
所以定稿时按 `doc_id` 折叠：同一篇文献的所有片段映射到同一个号，文献表每个 `doc_id`
只出现一次，代表条目取**字段最全**的那一条（不取第一条——第一条可能落在正文中间、
元数据抽取不全，用它当代表会让文献表缺字段）。

片段级的页码追溯信息保留在 `meta["writing_evidence"]` 台账里，不丢。

**文献表只列真正被引用的文献。** 检索到但没用上的留给你做参考，绝不混进文献表——
"表里有、正文没引"正是查重与评审会抓的硬伤。

**文献表不补全任何字段。** RAG 的文档元数据里没有期刊名、卷期、文献类型标识，
那就空着并逐条列出缺什么。一份"排版整齐但字段是编的"参考文献表，比一份明确标出缺什么更危险。

### 4. 待办标记在 Word 里标红

`【待作者补充：…】` 这类标记在导出的 .docx 里**加粗标红**。这不是装饰：
三万字初稿里如果待补处和正文长得一样，你根本找不到自己该补哪里，
而"哪里没有依据"正是这份稿子最需要被看见的信息。

## 四、验证：45 个检查器，13 条只针对写作质量

这个项目的纪律是：**提示词里提的每一条要求，都必须能被检查出来。**
只提要求不检查，等于给模型一个愿望。

本次为新增的四个章节蓝图（研究设计/实证结果/讨论/结论）配了 12 个检查器：

| 检查器 | 判定口径 | 严重度 |
|---|---|---|
| `check_method_specific` | 研究设计是否写到可复现粒度（具体数字与来源，而非「相关数据」） | major |
| `check_method_choice_reason` | 方法选择是否给出理由 | major |
| `check_method_no_textbook_dump` | 是否退化成教科书式的方法原理复述 | minor |
| `check_results_no_new_method` | 结果章是否引入了研究设计章未交代的方法 | major |
| `check_results_report_negative` | 是否只报显著结果 | minor |
| `check_disc_contrast` | 讨论章是否与既有研究对照（而非重复结果） | major |
| `check_disc_no_new_results` | 讨论章是否添了结果章没有的统计量 | major |
| `check_limitation_specific` | 局限是否具体（而非「存在一定局限性」） | major |
| **`check_conclusion_grounding`** | **结论里的数字必须能在正文找到** | **blocker** |
| `check_conclusion_traceable` | 结论条目是否标明依据章节 | major |
| `check_conclusion_no_innovation` | 结论是否出现不该由工具生成的创新点声明 | blocker |
| `check_overclaim` | 是否出现以「本文」为主语的夸大断言 | major |

**章间检查需要整篇稿件**（结果章 vs 研究设计章、结论 vs 正文），所以它们在
**验证阶段**才真正执行；起草阶段的单章自查会自动跳过——宁可跳过，也不要拿半篇文本
去比对而报出一堆假问题，假问题会让你连同真问题一起忽略。

### 一次真实生成的验证结果（《开题报告四》→ 科大讯飞案例）

```
致命 1 · 重要 5 · 轻微 12 · 提示 9 · 已自动修复 67 · 待人工 98
模型调用 47 次 · 186.9s · 提示 234 158 字符 → 回复 16 762 字符
```

真实抓到的典型问题（**全部是真问题**）：

* `writing.method_not_reproducible` —— 「基于生命周期理论的数据资产计量与价值评估模型构建」
  一章 0 处具体数字，全是从文献转述的方法原理。这正是"抄教科书"的实证。
* `writing.results_new_method` —— 核心分析章出现了研究设计章未交代的
  「机器学习、层次分析法、市场法」。
* `writing.lit_per_paper` —— 文献综述里多段仍是「一篇论文半句话」。

## 五、已知限制（请先读这一节）

1. **创新点、致谢需要你自己写。** 系统完全不生成，这是设计选择不是能力不足。
2. **结论是汇总草稿。** 每条结论都要你确认「这确实是我的意思」后才算定稿。
3. **`【待作者补充：…】` 必须处理。** 那是模型明确说"这里我没有依据"的地方，
   要么补上真实数据，要么删掉该句。**不要留着没有依据的断言交稿。** 
4. **参考文献字段要你补全。** 期刊名、卷期页码、`[J]`/`[M]`/`[D]` 类型标识，
   知识库里没有就不能编。
5. **排版是通行惯例，不是你们学校的模板。** 宋体正文／黑体标题／1.5 倍行距／A4 只是
   一个合理的默认值。真正的模板对齐要在拿到学校官方 .docx 之后做。
6. **不做查重与 AIGC 检测。** 这两件事本系统不做，也无法预测检测器结果。
7. **扫描版 PDF 无法入库**，`.caj`/`.nh` 需先转 PDF。
8. **RAG 知识库的覆盖范围决定了核心章的资料厚度。** 知识库里没有同主题文献时，
   相应章节会被标成"证据为 0，现在写不了"，而不是硬写。

**关于学术诚信**：系统守住的是"数字、引用、创新点不被代写代改"这类可机械校验的底线。
但论证是否成立、结论是否恰当、署名内容是否属实，**由署名人负责**。

## 六、开发中踩到的坑（都值得记下来）

### 1. `writer:plan` 从未被调用——写作能力从命令行完全走不通

`draft` 阶段原先只挂 `writer:draft`，而全项目没有任何地方调用 `writer:plan`。
于是 README 里写的 `run -s draft` **必然**报"没有找到写作大纲"。

最值得记的是它为什么没被发现：**每个智能体的单元测试都直接调自己，全绿。**
"每个部件都测过"不等于"它们被接起来了"。所以现在阶段到智能体的映射写成了一份显式清单
（`app/pipeline.py` 的 `STAGE_AGENTS`），并由 `tools/test_thesis.py` 端到端验证顺序。

### 2. 参考文献区识别不了 Markdown 的 `# 参考文献`

`find_references_block` 原先只认"整行等于 参考文献"，而系统生成的稿件写成 `# 参考文献`。
后果是连锁且**静默**的：

* 定稿重排时旧文献表没被切掉，于是**追加出第二份参考文献表**；
* 文献条目 `[1] 张三. …` 被当成正文角标，被误判成"模型编造引用"；
* 结论章的"数字必须在正文出现"检查把文献表里的年份页码也算进正文。

这是 `tools/test_thesis.py` 里那条"还原时丢掉旧的参考文献表"断言抓出来的。

### 3. 定稿后再重跑起草，两套编号空间会混在一份稿子里

`writer:references` 会把角标从证据池编号改写成连续编号。若在那之后再跑一次起草
（上次因余额/网络中断而重跑，是很常见的情形），旧章节带着"最终编号"、新章节带着
"池编号"——**同一个 `[7]` 可能指向两条不同证据，而外观上完全看不出来。**

修法：重跑起草前用 `references_final.mapping` 的逆映射把稿子还原回池编号空间。
逆映射时**键必须转 int**——落盘 JSON 会把字典键变成字符串，不转就会静默匹配不上，
而失败的表现是编号错乱，不是报错。

### 4. 模型服务的致命错误必须熔断

真实跑过一次，中途账户余额耗尽（HTTP 402）。当时的代码对**每个**剩余单元都再试一次：
白跑 6 次、多花两分钟、报告里堆出 6 条一模一样的失败记录，把真正的信息淹没在噪音里。

现在 `is_fatal_llm_error` 只认**明确的**致命标志（401/402/403、余额不足、密钥无效），
命中即停：记录一次、退出所有循环、说清楚。判错方向的代价不对称——
把致命当普通只是多试几次；把普通当致命会让整章其余小节全不写，而作者只看到"生成失败"。

### 5. 提示词里的例子怎么写，模型就怎么写

第一次完整生成出来的稿子里，引注全是 `（[21]）` 而不是 `[21]`。
原因是起草提示词的示例写成了 ``例如 `……（[1]）` `` ——**模型照抄了示例的括号**。

学位论文按 GB/T 7714 顺序编码制要求引注直接写作 `[1]`，不加中文括号。
两处都改了：提示词里的示例去掉括号，并在定稿环节加一次机械归一化
（`normalize_marker_wrapping`），把 `（[1]）` → `[1]`。归一化**只动括号、不动编号**，
括号里还有别的内容（如 `（见[1]）`）时不动——那种括号承载了语义。

顺带记一条顺序约束：归一化必须在编号重排**之前**做。反过来做的话，`（[1]）`
在重排时括号会被留在原地，得到 `（[3]）` 这种"重排过了但还没归一化"的中间形态。

### 6. 跨单元重复句

分单元写作的通病是后一个单元把前一个单元的话再说一遍。判据刻意保守：
只删**逐字相同且 ≥ 24 字**的句子。改写过的重复（"该结论表明……"与"这一结论说明……"）
不删——那是行文的正常变化，机械删除会破坏段落连贯。**唯一没有争议的重复就是一字不差的重复。**

### 7. 文献表把同一篇论文列了五遍——编号的单位错了

第一次完整生成出来的参考文献表，前五条是同一篇论文的五个片段。
根因是编号按**证据段落**分配，而文献表列的是**文献**：证据池里
`1=陈荣达(第1页) 2=陈荣达(第3页) …` 被原样搬进了文献表。

修法是定稿时按 `doc_id` 折叠（详见第三节 3.1）。

### 8. 参考文献字段补齐不能依赖上游做过

第一版把"补齐作者/题名/年份"放在起草阶段，结果起草中途新检索到的证据没被补上，
定稿生成的 49 条文献**全部显示"缺字段"**——而知识库里明明有这些字段。
文献表退回用 RAG 那句拼好的 `citation` 串，里面还混着作者单位与邮编。

两处都改了：起草阶段收尾再补一次；更重要的是 **`writer:references` 自己也补一次**。
理由是这个字段的唯一消费者就是文献表——依赖上游做过，就会出现"上游漏了一步、
下游整表连锁失效"这种当场看不出来的故障（缺字段的标记长得像"这条文献元数据本来就没有"）。
补元数据是纯查询、不花钱，放在消费端才稳。

### 9. 定稿这一步本身也必须幂等

`writer:references` 会把角标从池编号改写成连续编号。直接再跑一次，它会把正文里
那些**已经改写过的编号**当成池编号去查表——查到的是另一批证据。
所以重跑前先按上次落盘的 `references_final.mapping` 做逆变换还原。

`writer:draft` 和 `writer:references` 都需要这道还原，所以逆映射函数放在
`app/writing/citations.py` 里共用一份。

### 10. 一章一个单元时，蓝图语步名不能当小节标题

起草无小节章节时，最初的实现拿蓝图的结构骨架名（「确立研究领域」）当 `## ` 小节标题。
那些是**修辞步骤的名字**，出现在成稿的目录里会非常突兀。

现在整章作为一个单元，骨架名只作为"本章要覆盖这几件事"的侧重提示，
不会变成标题。

## 七、怎么验证这套系统本身

```powershell
# 一键生成链路：开题解析 → 引用编号 → 分段起草 → 结论 → 文献表 → 导出（89 项）
.\run_python.cmd tools\test_thesis.py

# 各写作智能体的纪律（97 项，含 12 项假件精确构造的分支）
.\run_python.cmd tools\test_writer.py

# 写作检查器正反例、蓝图注入、起草闭环
.\run_python.cmd tools\test_writing_quality.py
.\run_python.cmd tools\test_writer_integration.py

# 其余回归
.\run_python.cmd tools\test_checks.py
.\run_python.cmd tools\test_fixer.py
.\run_python.cmd tools\test_format.py

# 验证测试隔离是否生效（每个测试跑完 projects 数量都应不变）
.\run_python.cmd tools\inspect_data.py
```

`tools/test_thesis.py` 的设计要点：它**不测各个智能体的内部逻辑**（那是
`test_writer.py` 的事），只测"它们有没有被接起来、顺序对不对、整条链路能不能产出
一份带文献表与结论的 .docx"。这两类测试缺一不可——

> **每个部件都测过，不等于它们被接起来了。**
